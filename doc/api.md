# API

HTTP API (access token: `Authorization: Bearer <token>`, see `services.md` for authentication):

- `POST /api/games/{id}/messages` (`ApiGameMessagesController`, through `Service/Api/PlayerMessageSender`, shared with the MCP tools: checks, dispatch and the problem of a rejected message, `ApiProblemException`): a player of the game sends any public action message, `{"type": "pass_opportunity", "payload": {...}}`. The type is the snake case short name of the message class; the payload holds its constructor arguments in snake case (serializer name converter). `Service/Api/ApiMessageFactory` builds the message: the game comes from the URL, the player (sender) is the authenticated player (the payload cannot hold `game_id` nor `player_id`); the target of an effect is in the payload (`target_player_id`…). The controller only reads ids before dispatching (see `GameLockMiddleware`). Versions: the `ETag` of the response is the version of the game once the message is handled (`"12"`); with `If-Match` (a single ETag of the game, or `*`), the message is rejected with a 412 (`stale_version`) if the game has changed since, an independent message excepted. Responses: 204 once handled; errors are problem details (`application/problem+json`, `type` from the exception): 400 invalid body, type, payload (`invalid_payload`: structure of the payload, with `violations`) or `If-Match` (`invalid_if_match`); 401 no token; 403 not a player of the game; 404 unknown game; 409 forbidden by the rules in the current state (`Exception/Rules`, `WorkflowException`, workflow transition not enabled); 412 stale version; 422 payload referring to nothing in the game or with invalid values (`validation_failed`: constraints of the message, with `violations`). A violation has a `property_path` (snake case) and a `message`.
- `GET /api/actions` (`ApiActionsController`): the catalogue of the public messages, the JSON schema of the payload of each type (`MessageSchemaFactory`). Public (no token) and cacheable. The schemas are also committed in `schemas/messages` (`bin/console app:message-schemas:dump`), the snapshot of the contract of the API: a test fails when they differ from the messages.
- `GET /api/games/{id}` (`ApiGamesController`): the state of the game as the authenticated player sees it, or an account that does not play it (a spectator: `viewer_id` null, nothing but what is public, no available action; it watches the game from then on, see `services.md`; a guest or a bot gets a 403), (players with their name, the clan of their stronghold and their nobori, `banner`; `training`: a game against the house bot), with a link to the Mercure hub (`Link: <…>; rel="mercure"`, `Mercure\Discovery`), built by `View/GameViewFactory::create(Game, ?Player $viewer)` into the readonly DTOs of `View/Model` (`GameView`, `PlayerView`, `StackView`, `CardView`) and serialized in snake case. A read goes neither through the bus nor through `GameLockMiddleware`. Same errors as the messages API (401, 403, 404). The `ETag` is the version of the game (also `version` in the view): the view only depends on the state and the viewer, so a player sending the ETag they have (`If-None-Match`) gets a 304 until the game changes; the response is `private, no-cache`. The visibility rules only depend on the state, never on the game place, and those of the cards are written once, in `View/Visibility` (shared with the log; a viewer who is not a player, null, sees what every player sees): decks and the opponents' hands are sent as counts (`cards: null`), a face-down card has no `code` (except a province for its owner, and a card set aside for the player of its stack: the player who removed it from the game, the owner of the card it lies under) but its `side` (conflict, dynasty, province…: its back); the secret information of `PlayerState` (`pendingHonorBid`, `strongholdProvinceId`) goes to its owner only (in the factory); everything else is public. A card carries its controller (`controller_id`); a stack of cards under a card, that card (`host_id`). Cards are sent by code: the client reads them from `GET /api/cards`. New secret information must be stored apart from what is public, and masked in the factory. `available_actions` lists the types of the public messages the viewer can send now (`AvailableActionsResolver`, none once the game has ended): an action is listed when its handler's `assertAvailable()` passes, its payload can still be rejected. `special_actions` lists every special message (`{"type", "card_ids"}`, `Service/SpecialActionsResolver`) with the active cards of the viewer whose script needs it (`AbstractCardScript::getSpecialActions()`, see `card-scripts.md`); none for a spectator.
- `GET /api/cards` and `GET /api/cards/{code}` (`ApiCardsController`): the cards as printed (`LogicalCard`), every card sorted by code or one card, built by `View/LogicalCardViewFactory` into `View/Model/LogicalCardView` (code, printed attributes, `ability_timings`, `ability_granted_to_attached` (read from its script), `image_url`: its image on the CDN of the cards, `<CARD_IMAGES_URL>/cards/<code>.webp`, see `services.md`; not the packs), serialized in snake case. Public (no token) and cacheable, like `GET /api/actions`; 404 `card_not_found` for an unknown code.
- `POST /api/guests` (`ApiGuestsController`): anyone gets a guest account, a human user with the name they chose (`{"name": ...}`, 1 to 64 characters) and no identity, with a session token: 201 `{"user_id", "name", "token"}` (`View/Model/GuestView`), the only time the token is sent. Public. Each attempt counts against the limit of the creations of users of its IP (30 an hour, a sliding window, shared with `POST /api/accounts`: `user_creation_ip` in `config/packages/rate_limiter.yaml`), an invalid body excepted: 429 `too_many_attempts` with `Retry-After`.
- `POST /api/accounts` (`ApiAccountsController`): a human creates the account they sign in to, `{"username", "password", "clan"}` (the preferred clan, a Great Clan: the account gets a copy of its starter deck). A guest sends their token and keeps their user and their name (no `name` in the body); anyone else also sends their name at court (`"name"`, 1 to 64 characters) and gets a new user. 201 `{"user_id", "name", "username", "preferred_clan", "settings", "token"}` (`View/Model/AccountView`, also sent by `POST /api/sessions`) with a new session token. Errors: 400 `invalid_payload` (structure: fields missing, not strings or unexpected), 422 `validation_failed` (values, checked by the Validator on `Model/AccountRequest`, and a username taken whatever its case: "This username is taken."), 409 `already_registered` (a token of a user who has an account, or of a bot), 401 an unknown token, 429 `too_many_attempts` (each attempt with a body of the right structure counts against the limit of the creations of users of its IP, shared with `POST /api/guests`). Public.
- `POST /api/sessions` and `DELETE /api/sessions/current` (`ApiSessionsController`): signing in, `{"username", "password"}` (the username whatever its case): 201 with a new session token, like an account created; 401 `invalid_credentials`, the same for an unknown username and a wrong password (an unknown username hashes the password too, so that the time does not tell). Each attempt counts against two limits (`config/packages/rate_limiter.yaml`, sliding windows: 5 a minute by username, 20 a minute by IP), a success resets the count of the username: 429 `too_many_attempts` with `Retry-After`. Signing out revokes the session token of the request (204); an API key is not revoked this way (409 `not_a_session_token`). Signing in is public.
- `GET /api/oauth/providers`, `POST /api/oauth/{provider}/authorizations`, `POST /api/oauth/{provider}/sessions` and `GET`, `PUT`, `DELETE /api/self/linked-accounts[/{provider}]` (`ApiOAuthController`): signing in with a provider of identities (OAuth2: authorization code grant with PKCE, the API being the confidential client, `Security/OAuth/OAuthFlow`), once the account is linked to an identity there; accounts are created with a username and a password only. The web client starts a flow (`{"purpose": "sign_in" | "link"}`, with the token of the account to link: 201 `{"authorization_url", "state"}`), sends the human to the provider, which sends them back to the web client (`/oauth/{provider}/callback`, the redirect URI registered at the provider, on the origin of the request); the web client checks the state, then sends `{"code", "state"}` to sign in (201 with a session token, like `POST /api/sessions`; 401 `not_linked`; counted against the limit of its IP) or to link (`PUT /api/self/linked-accounts/{provider}`: 201, 200 when linked already, 409 `provider_already_linked` / `identity_already_linked`). The state (256 bits, used once, 10 minutes in the pool `cache.oauth_state`) keeps the provider, the purpose, the user linking, the redirect URI and the code verifier: 400 `invalid_state` when it does not match. The API exchanges the code (`client_secret`, code verifier) and reads the identifier of the identity; nothing the provider issues reaches the web client. 400 `authorization_failed` when the provider refuses the code, 502 `provider_unavailable`, 403 `account_required` for a guest or a bot, 404 `unknown_provider` (also a provider without credentials). The clients of the providers (`Security/OAuth/OAuthProviderFactory`, league/oauth2-client; `Security/OAuth/Provider`: Google asking `openid` only, Discord `identify`) read their credentials from `OAUTH_<PROVIDER>_CLIENT_ID` and `_CLIENT_SECRET` (empty: disabled) and send their requests through the Guzzle client `app.oauth.http_client`, a `MockHandler` in the tests.
- `POST /api/bot-games` (`ApiBotGamesController`): a game against the house bot, without the queue: the user plays a deck they can use (`{"deck_id": ...}`), the bot another starter deck drawn at random; `Service/GameLauncher/BotGameLauncher` dispatches `CreateGame` then `JoinGame` for the user and the bot. 201 `{"game_id", "player_id", "opponent": {"user_id", "name", "deck_id"}}` (`View/Model/BotGameView`); 409 `game_in_progress` while a game of the user has not ended (`GameRepository::hasInProgress()`, the replays left out), 409 `already_queued` while they wait in the queue, 422 `deck_not_found`, 503 `bot_unavailable` when the house bot (`HOUSE_BOT_ID`) is not a bot user.
- `GET /api/self` (`ApiSelfController`): the authenticated user, `{"user_id", "name", "username", "preferred_clan", "settings", "banner", "unlocked"}` (`View/Model/SelfView`, `username` and `preferred_clan` null for a guest or a bot; `settings`: `{"card_display": "drawn" | "images", "theme": "auto" | "light" | "dark", "tutorial": bool, "seen_tips": [...]}` (whether the tips of the tutorial show, and the ids of those seen, written by the web client: `[a-z0-9_]{1,64}`, 200 at most, the list sent replacing the one stored); `banner`: `{"mon", "pattern"}`, their nobori; `unlocked`: `{"mons": [...], "patterns": [...]}`, what they may choose for it, in the order of the enums). `PATCH /api/self` `{"name", "preferred_clan", "settings", "banner"}` (any of them; a setting or a part of the nobori left out is kept): changes their name at court (1 to 64 characters), their preferred clan, their settings or their nobori (400 `invalid_payload`, 422 `validation_failed`: a mon or a pattern they have not earned, "You have not earned this mon yet."), 200 with the user. `DELETE /api/self`: a human deletes their account (204; 403 `account_required` for a guest or a bot), no authentication asked again: `Security/AccountDeleter` takes them and their bots out of the queue, concedes the games they play (`ConcedeGame` through the bus), deletes their invitations, tokens, linked identities and decks (a deck played in a game only loses its name: the player keeps it), and anonymizes the users (`User::anonymize()`: "A former player", no username, password, clan nor settings, the date of the deletion in `deletedAt`), which stay so that the games keep their players. `GET /api/self/trophies`: every trophy of the catalogue, in its order (`View/TrophyViewFactory` into `View/Model/TrophyView`: `trophy`, its reward `reward_mon` or `reward_pattern`, `earned`, `earned_at`, `game_id`; `no-store`), whose names and goals the web client writes. `GET /api/self/subscription`: their subscription to the Mercure hub (`View/Model/SubscriptionView`: the public URL of the hub, their topic and when their subscriber token expires, the token for an hour in the cookie of the hub; `no-store`), see `services.md`. `GET /api/self/games`: their games, in progress or ended (not the replays), the last joined first (`View/Model/UserGameView`: id, their `player_id`, `version`, `ended`, `friendly`, the users in player order, the `seats`: each player's user, name, clan of their stronghold and whether a bot plays; once ended, `ended_at`, `winner_id` and `victory_condition`), so that a user matched by the queue finds their game and the history lists their games (`UserGameViewFactory::createAll()`: `GameRepository::findByUser()`, then the clans, two queries).
- `GET /api/decks`, `GET /api/decks/{id}`, `POST /api/decks`, `PATCH /api/decks/{id}` and `DELETE /api/decks/{id}` (`ApiDecksController`): the decks the authenticated user can use (their own not deleted and the starter decks; the others are not found, 404 `deck_not_found`), the renaming of one of their own decks (`{"name"}`, trimmed, 1 to 255 characters: 400 `invalid_payload` otherwise, with `violations`; 200 with the deck; 404 for a starter deck), the deletion of one of their own decks (204; 404 for a starter deck, 409 `deck_in_queue` while they wait with it, 409 `deck_in_tournament` while it is registered in a tournament neither ended nor cancelled), and the import of a deck: `{"name": ..., "format": "emeralddb", "cards": {"<card id>": <quantity>}}`, 201 with the deck (`View/Model/DeckView`: its id, name, owner and cards, its `stronghold` (a code, null without one) and the `clan` of the stronghold, read by `DeckViewFactory` in one query for every deck listed). `Service/Deck/DeckImporter` converts the ids of the format to codes (`Service/Deck/DeckFormatInterface`, one tagged service per format: `codes` for the codes of the engine, `emeralddb` through the external cards), then checks the deckbuilding rules of the Stronghold format (`Service/Deck/DeckConstructionValidator`, not the banned and restricted lists). A deck with the same cards as one of the user's (`contentHash`) is not created: the API answers that deck with a 200 (its name kept), or restores it with a 201 when they had deleted it (with the name of the import); a deck with the cards of a starter deck or of another user is imported as usual (`Model/ImportedDeck`, `Enum/DeckImportOutcome`). Errors: 400 `invalid_payload` (structure, with `violations`), 422 `invalid_deck` (unknown format, card unknown to the format, broken rule; `violations` on `format`, `cards[<id>]` or `cards`). A deck of EmeraldDB is also downloaded from the URL of its page (`Service/Deck/EmeraldDbDeckFetcher`: `/decks/<decklist id>` or `/builder/<deck id>/edit`, read from `/api/decklists/<id>` through the scoped HTTP client `emeralddb.client`, no redirection followed; `InvalidDeckUrlException` for another URL or a deck not shown, `DeckSourceUnavailableException` when EmeraldDB cannot be reached or answers no deck), then imported in the format `emeralddb`: `{"name": ..., "url": ...}` (the name of EmeraldDB unless given; no `format` nor `cards` with a URL), 422 `invalid_deck` with a violation on `url` for a URL naming no deck, 502 `deck_source_unavailable`; also from the console (`app:deck:import <url> --user=<id or username> [--name=]`).
- `GET /api/self/decks` and `GET /api/self/decks/{id}` (`ApiDecksController`, `View/OwnedDeckViewFactory`): the decks of the user (their own not deleted, not the starter decks: 404 `deck_not_found` for those and the decks of others), each `{"deck", "record"}` (`View/Model/OwnedDeckView`): the deck as `GET /api/decks/{id}` gives it, and its record (`DeckRecordView`), read from the games of the user played with it (every game but the replays, in three queries whatever their number): `played` (the games ended), `won`, `lost` (a game ended without winner is neither), `in_progress`, `ranked_won` and `ranked_lost` (the standard games: neither friendly nor against the house bot), `last_game` (`{"game_id", "ended_at", "won", "opponent_clan"}`, null before the first game ended), `endings` (won and lost by victory condition, in the order of the enum) and `opponents` (won and lost by clan of the stronghold of the opponent). The list comes the last played first, then the decks never played. The titles of the cards are read by the client from `GET /api/cards`.
- `GET`, `POST` and `DELETE /api/queue` (`ApiQueueController`): the matchmaking queue. A user joins it with a deck they can use (`{"deck_id": ...}`, 204; 409 `already_queued`, 409 `game_in_progress` while a game of theirs has not ended (`Exception/Api/GameInProgressException`, the MCP tool `join_queue` too): they finish it first, 422 `deck_not_found`) and is matched at once when another candidate waits; `GET` gives the deck they wait with (404 `not_queued` once matched or left). The host of an invitation joins it with its id (`invitation_id`), a friend with its code (`invitation_code`), the bot with the key of the invitation (nothing to add): they are matched together only (422 `invalid_invitation`: unknown, expired, used, not theirs, or its seat taken). The host leaving the queue cancels their invitation. A player of a match of a tournament joins it with the match only (`{"match_id": ...}`, the deck of their registration: 400 `invalid_payload` with any other key), replacing any other wait, until 10 minutes after the round has begun (422 `invalid_match`: unknown, not theirs, not of the current round, played already, or too late; 409 `game_in_progress`); `GET` gives the match they wait with too (`match_id`, null without one). `GET /api/queue/count`: how many players wait in the open queue for an opponent, the user left out (the candidates of an invitation or of a match wait for each other only), `{"waiting": n}` (`no-store`), so that a player sees that joining starts a game at once.
- `POST /api/invitations`, `GET` and `DELETE /api/self/invitation`, `GET /api/invitations/{code}` (`ApiInvitationsController`, `Service/Invitation/InvitationIssuer`): an account (403 `account_required` for a guest or a bot) invites its bot or a friend to a friendly game (`{"kind": "bot" | "friend"}`, 201 `View/Model/InvitationView`: the code of a friend, or the bot and its key, sent once), which cancels its previous invitation: a host has one waiting at most, read (without the key; once expired, no longer: the web client offers a new one) or cancelled (404 `invitation_not_found`). The bot is the first bot of the account, else created ("<name>'s bot"). Anyone with the code reads the name of the host and whether it can be used (`pending`, `expired`, `used`; 404 once cancelled): public.
- A replay (its copy) is read by the user who follows it only, as its player: anyone else gets a 404 (`Game::isHiddenFrom()`, the MCP tools too), its view has no available action nor special action, and it has no abandonment (404).
- `GET /api/tournaments`, `GET /api/tournaments/{id}`, `POST /api/tournaments`, `POST /api/tournaments/{id}/cancellation`, `GET /api/self/tournaments`, `PUT` and `DELETE /api/self/tournaments/{id}` (`ApiTournamentsController`, `Service/Tournament`, see `services.md`, "Tournaments"): the tournaments are public (the two `GET` of `/api/tournaments`, visitors included: `PUBLIC_ACCESS`), the same for every reader; what concerns the reader is under `/api/self`. The list: the tournaments to be played (open, locked, in progress) and the cancelled ones that would not have begun yet, the first to begin first (`View/Model/TournamentSummaryView`: id, `starts_at`, `locks_at`, `status`, `format`, the `organizer` (`user_id`, `name`, `banner`), `entrants`, `max_entrants`; the number of players of every tournament in one query, `TournamentViewFactory`). A tournament (`TournamentView`): the same without `entrants`, with its `players` in their order of registration (`TournamentUserView`: their name and nobori, never their deck nor their clan), and, once locked, `size`, `round_count`, `current_round` (0 until it begins), `join_deadline` (until when the players of the current round join the queue), `winner` (once ended) and the `rounds` that have begun (`TournamentRoundView`: `number`, `matches`, `TournamentMatchView`: `id` (to join the queue with), `table`, `players` (one for a bye), `game_id`, `winner_user_id`, `outcome` (`game`, `bye`, `forfeit`, `no_result`), `victory_condition`, `waiting`: the user ids of its players in the queue with it): the pairings of a round stay secret until it begins; 404 `tournament_not_found`. An account (403 `account_required` for a guest or a bot) creates one, `{"starts_at"}` (RFC 3339, `Z` or an offset, stored in UTC; 400 `invalid_payload` for anything else or another key, a date that does not exist included), 201 with the tournament; 422 `invalid_start` off the hour or the half hour or less than 12 hours ahead, 409 `tournament_already_organized`, 409 `tournament_too_close` (with `other_starts_at`). Its organizer cancels it (200 with the tournament; 403 `not_organizer`, 409 `tournament_closed` once locked or cancelled already). `GET /api/self/tournaments`: the registrations of the user in the tournaments that have not ended, cancelled ones included (`TournamentEntryView`: the `tournament` as listed, `deck_id`, `deck_name`, `registered_at`, `eliminated`). `PUT /api/self/tournaments/{id}` `{"deck_id"}`: registers the user (201) or changes the deck of their registration (200), with the registration; 422 `deck_not_found` (a deck they cannot use), 409 `tournament_closed` (locked or cancelled), 409 `tournament_full` (64 players). `DELETE`: unregisters them (204), until it locks, or at any time once it is cancelled; 404 `not_registered`, 409 `tournament_closed`. `GET /api/tournaments/{id}/calendar.ics`: the tournament as an iCalendar file (`text/calendar`, downloaded as `kyuden-tournament-<date>.ics`), public since calendars send no token (`Service/Tournament/TournamentCalendar`, see `services.md`); 404 `tournament_not_found`. Every read is `no-store`.
- `GET /api/games/{id}/log?since={version}` (`ApiGamesController`): the log of the game after a version (0 by default) as the authenticated player reads it, or a spectator (only what is public) (`View/GameLogViewFactory`): the messages handled on the game (`version`, `type`, sender `player_id`, never the payload), each with its entries (`template`, `params`) masked for the reader. Same errors and `ETag` as the view, 400 `invalid_since`, 400 `invalid_wait`. It is also a long-poll: with `wait={seconds}` (0 to 30), the response waits until the version is greater than `since` (`Service/GameUpdateWaiter`, polling the version in the database through the Symfony clock), then sends what changed, or the log as is (no message, or a 304) once the time is up; a game that has ended answers at once.
- `GET` and `POST /api/games/{id}/abandonment` (`ApiAbandonmentController`, `Service/Abandonment/AbandonmentClaimer`): whether the authenticated player may end a game their opponent no longer plays (`View/Model/AbandonmentView`: `awaited_player_ids`, `claimable_at`, `claimable`; `no-store`: it depends on the time), then ending it (204 with the `ETag` of the game, which has ended: the player wins), see `game-flow.md`, "Abandoned games". 403 for whoever does not play it, 404 unknown game, 409 `game_not_abandoned` while the opponent may still play (with the time from which they may not) or when the game waits for the player, 412 when the game changes meanwhile.
- `GET /api/games` (`ApiGamesController`): the games in progress (started, not ended), the last started first, for an account to choose one to watch (403 `account_required` for a guest or a bot): `View/GameInProgressViewFactory` into `View/Model/GameInProgressView` (id, `version`, `place`, `friendly`, the players with their name, the clan of their stronghold and whether they are a bot, the number of `spectators`), in three queries whatever their number. `GET /api/games/{id}/spectators`: the accounts watching the game, in their order of arrival (`View/Model/SpectatorView`: `user_id`, `name`), for whoever reads the game (a player or a spectator, who watches it then); `no-store`. `DELETE /api/games/{id}/spectators/self`: the spectator stops watching (204).
- `GET`, `POST /api/games/{id}/replay` and `POST /api/games/{id}/replay/proceed` (`ApiReplayController`): the replay of a game that has ended, for one of its players (see `services.md`, "Replay"). `POST …/replay` starts it again from the beginning (the replay they followed deleted), `POST …/proceed` continues it; both replay up to the next action of the player, which the replay stops before, or up to a version (`{"until_version": n}`, whoever sends the messages: going back is starting again up to it). They answer where it stands (`View/Model/ReplayView`: the game, the copy (`replay_game_id`) and the player in it, `version`, `total`, `next`: the next action of the player, `{"version", "type"}`, whose entries the log of the original game tells, and `ended`; `no-store`), as does `GET` (404 `replay_not_found` before it starts); the board is the view and the log of the copy, as its player. 403 for whoever did not play the game, 404 for an unknown game or a replay, 409 `game_not_ended`, 409 `replay_ahead` (proceeding to a version before the replay), 409 `replay_diverged` (a record the engine refuses, with the `version` the copy stands at), 400 `invalid_payload`. `GET /api/games/{id}/replay/log`: the log of the original game as the player reads it (`GameLogViewFactory`), its ids translated into those of the copy, every message of it, those not replayed yet included (`no-store`).
- MCP server (`symfony/mcp-bundle`, `config/packages/mcp.yaml`): `/api/mcp` (HTTP transport), for the programs playing as a bot (`ROLE_BOT`, API key in `Authorization: Bearer`, under the firewall of the API). Its protection against DNS rebinding accepts any host and checks the `Origin`: the host is checked by Symfony for the whole application, against `SYMFONY_TRUSTED_HOSTS` (regular expressions separated by commas, localhost by default; another host gets a 400). Its tools are services of `src/Mcp` with a `#[McpTool]` method: the doc comment of the method and its `@param` describe the tool, the types and `#[Schema]` give the schema of the arguments, which the server checks before the call; a tool returns an array (the structured content) and reports an error with a `ToolCallException`. The user is read through `Security`. The tools give a bot what the HTTP API gives a player, so that an agent needs nothing else: `list_decks`, `join_queue` / `leave_queue` (`Service/MatchMaking/MatchMakingQueue`, shared with `/api/queue`; with the key of an invitation, the bot waits for its host only), `list_my_games` and `wait_for_game` (the long-poll on the games of the bot, until one is in progress: `Service/GameStartWaiter`), `get_game` (the view of `GameViewFactory`), `get_cards` (cards by code, up to 50), `list_glossary_entries` / `get_glossary_entries` (the glossary of the rules entry by entry, by title or term: `Service/Rules/Glossary`), `wait_for_update`, the long-poll on the log (`Service/GameUpdateWaiter`, `GameLogViewFactory`), and `end_abandoned_game` (`AbandonmentClaimer`, the opponent of the bot no longer playing). A list is returned in an object (`{"games": [...]}`), the structured content of a tool being an object. Each public message is also a tool named after its type (`Mcp/MessageToolLoader`, an `mcp.loader` registering a `Mcp/MessageTool` per message): its arguments are the schema of the payload (`MessageSchemaFactory`) with `game_id` and an optional `expected_version`; it returns the new `version`, and a rejected message is a tool error whose text is the problem of the HTTP API. A new public message is a new tool, with nothing to write. The bundle builds PSR-7 messages with `nyholm/psr7`. What a bot is told comes from the server, so that any MCP client plays with a prompt of one line: the `instructions` of the server (how to play: the tools, the loop, the engine as a board, conceding on an error), the rules as resources (`Mcp/RulesResources`: `kyuden://rules/learn_to_play`, `timing_and_gameplay`, `card_clarifications`, read from `doc/`) and the prompt `play` (`Mcp/PlayPrompt`, the line the screen of an invitation shows). `agent/` makes Claude Code play as a bot through this server (`agent/play.sh <API key> [deck]`, with `mcp.json`): it runs in an empty temporary directory, nothing of the repository, with the tools of the server and the reading of its resources only.
- Console commands (`src/Command`) drive the engine; `app:game:log <id> [--as=<user>]` shows the log as a player (or a spectator) reads it.
