# Architecture

How the engine is built: the domain model, its state, the pipeline every action goes through, the workflows and the log of a game. The rest: `api.md`, `game-flow.md`, `card-scripts.md`, `services.md`, `web-client.md`.

## Domain model (`src/Entity`)

- `LogicalCard`: the card as printed (title, cost, text), grouped in `Pack` via `Printing`. A `Pack` belongs to a `Cycle` (the core set, the clan packs, a cycle of chapter packs…), at its `position` in it; the cycles are ordered by their own `position`. What its text means for a game in progress is its script (see `card-scripts.md`): the timings of its triggered abilities among others.
- `PhysicalCard`: one copy of a card in a game, owned by a `Player`. Mapped superclass with one subclass per type in `src/Entity/CardTypes` (Conflict, Dynasty, Province, Role, Stronghold).
- `Stack`: ordered collection of physical cards (deck, hand, province, etc.; see `Enum/StackType`). The top card has the highest `position`. The stacks of the cards set aside out of play (`StackType::isSetAside()`) are created when a card first goes there (`Service/SetAsideStacks`): the cards a player has removed from the game (`RemovedFromGame`, one per player), and the cards under a card (`Underneath`, one per card, of the owner of that card, which it names: `Stack::host`, removed with it). When order matters, use `getOrderedCards()` / `getTopCards()`: the order of `getCards()` is not kept in sync with positions (e.g. after `moveCard()`).
- Shuffling (`Service/StackShuffler`, never `Randomizer::shuffleArray()` on cards directly) makes the players lose track of the cards: it deletes them and creates them again in random order with new ids (same logical card, player, stack and orientation, fresh state), so that an id seen before cannot be followed into a shuffled deck. Redistributing the cards of the provinces (`RedistributeProvinceCards`) gives new ids the same way. Code holding a card of a stack across a shuffle must read it again from the stack.
- `Enum/Orientation`: physical orientation of a card (`FaceDown`, `FaceUp`, `Sideways`, `UpsideDown`), stored on `PhysicalCard`. A new card takes the initial orientation of its class (`getInitialOrientation()`: face down, except stronghold and role); afterwards only workflow transitions change it.
- `Game`: friendly or not (`friendly`: a game of an invitation, not ranked), against the house bot or not (`training`: a game of `POST /api/bot-games`, not ranked), both set by `CreateGame`, a standard game being neither (`isStandard()`: a game of the queue); carries a `version`, the number of messages handled on it (incremented with each `Event`, so that the events of a game are numbered from 1, and when it last changed, `updatedAt`), and its own random generator (`getRandomizer()`, seeded by `CreateGame::seed`, engine state saved with the game) for every random draw (shuffles, first player, random discards, ids of the cards and stacks it creates: `generateId()`, salted by the id of the game, so that a game replayed under another id draws the same values without creating the same ids), so that replaying the event log gives the same game. Never draw outside of it. A game may be the replay of another one (`replayOf`, for the user who follows it, `replayUser`): a copy rebuilt from the events of a game that has ended (see `services.md`, "Replay").
- `Deck`: quantity by card code; each copy becomes a physical card when a game starts (`Deck::getCardCodes()`). A deck belongs to the user who imported it; a deck without owner (the starter decks, `fixtures/starter_decks/<deck id>.json`) can be used by every user. An account gets its own copy of the starter deck of its preferred clan when it is created (`Service/Deck/StarterDeckCopier`). Its `contentHash` (SHA-256 of a line `code:quantity` per card, sorted by code: `Deck::hashCards()`, kept in sync by `setCards()`) identifies its cards whatever its name: a user does not import the same cards twice (see the API). Its owner deletes it (`Service/Deck/DeckDeleter`): a deck never played is removed, a deck played in a game or registered in a tournament stays for its players, marked deleted (`deletedAt`): nobody can use it any more (`isUsableBy()`), and importing its cards again restores it; a deck waiting in the queue or registered in a tournament still to be played is not deleted.
- `ExternalCard`: links the id of a card in an external database (`Enum/CardSource`, e.g. EmeraldDB) to a `LogicalCard`, to import the decks built there; loaded from `fixtures/external_cards/<source>.json` (card code by external id).
- `Event`: persisted record of every handled action, numbered by the version of its game. It holds the payload of the message, secret information included (the seed of `CreateGame`, secret bids…): it is never shown to the players, who read the log of the game (see below).
- `GameLogEntry`: a line of the log of a game, what changed in it (see "Game log").
- `Candidate`: a player waiting in the matchmaking queue, with the invitation they wait with, if any.
- `Tournament`: a tournament an account organizes (`organizer`), with its start only (`startsAt`, UTC: no name nor description, nothing to moderate), its format (`Enum/TournamentFormat`: single elimination), its status (`Enum/TournamentStatus`: open, locked, in progress, ended, cancelled) and the seed of its draws (32 random bytes, stored like that of a game). It locks one hour before it begins (`getLocksAt()`, `isOpenAt()`): registrations, decks and cancelling no longer change. `TournamentEntry`: a player registered in a tournament (once per tournament), with the deck they play all of it with. See `services.md`, "Tournaments".
- `Spectator`: an account watching a game (its key: the game and the user), with when it arrived and when it last read the game; not part of the game (no event, no log), see `services.md`.
- `Invitation`: an invitation of an account to a friendly game, for its bot (an API key limited to it) or for a friend (a code: `Security/InvitationCode`); open, used once (the game it led to), expiring after 24 hours. Its host and its guest are matched together only (see `services.md`).
- `LinkedAccount`: an identity at a provider (OAuth2, `Enum/OAuthProvider`: Google, Discord) linked to an account, which then signs in with it: only the identifier of the identity at the provider (`subject`), no personal data; an identity is linked to one account at most, an account to one identity of each provider at most.
- `EarnedTrophy`: a trophy a user has earned (`Enum/Trophy`, the catalogue: `TROPHIES.md`), once, with when and the game it was first earned in (`SET NULL` should the game go), written by `Service/Trophy/TrophyCase` only, which unlocks its reward for the nobori at the same time (`Trophy::getReward()`: a mon or a pattern); deleted with the account (`forget()`). See "Trophies".
- `User`: an account, human or bot (`Enum/UserType`); a bot is owned by a human. Its id is its user identifier (a UUID, except the users of the fixtures). Its `name` is its name at court, what the other players see (not unique). A human signs in with a `username` (`[A-Za-z0-9_]{3,32}`, unique whatever its case: `usernameCanonical`) and a password (8 to 4096 characters, hashed by the `auto` hasher of Symfony); a human without a username is a guest (`isGuest()`), who becomes an account by registering (`register()`, `Security/AccountRegistrar`): the same user, so their games, decks and tokens stay theirs. An account has a preferred clan (`preferredClan`, one of the Great Clans: `Enum/Clan::greatClans()`), chosen when it is created and changed at any time; null for a guest or a bot. A user has settings (`settings`, JSON read through `Model/UserSettings`: a missing setting takes its default), for now how the web client draws the cards (`cardDisplay`, `Enum/CardDisplay`: `drawn` or `images`) and whether it is light or dark (`theme`, `Enum/Theme`: `auto`, `light` or `dark`), and the tutorial of the games against the house bot (`tutorial`, on by default, and `seenTips`, the ids of the tips seen, the catalogue being the web client's). A user has a nobori (`Model/Banner`, the columns `banner_mon` and `banner_pattern`): the vertical banner the other players see, a mon (`Enum/Mon`: the ensō or a Great Clan) on a pattern (`Enum/BannerPattern`: `none`, `plain` or a traditional pattern), the ensō without pattern to start with. They choose among what they have earned (`Service/Nobori/NoboriCollection`: the ensō and `none` for everybody, plus what is stored in `UnlockedMon` and `UnlockedPattern`, one row per user and value, written by `unlock()`); they earn them with trophies (`EarnedTrophy`), and `app:nobori:unlock <user> <value>…` also gives them by hand. The house bot shows the mon of the clan of its stronghold on a plain nobori (`NoboriCollection::bannerInGame()`), computed, not stored. A `Player` and a `Candidate` belong to a user (`Player::getUserId()` reads the id without loading the user); a player also carries when they last read their game (`lastSeenAt`, see `game-flow.md`, "Abandoned games"); a user is a candidate at most once. `AccessToken`: a token of a user, stored as its SHA-256 hash, either a session or an API key (`Enum/AccessTokenType`), with when it was last used (`lastUsedAt`); the session of an account expires once unused for 30 days (`AccessToken::isExpired()`), the session of a guest (their only key to their user) and the API keys never; only a bot gets API keys, so that a program playing through one is known as a bot (`ROLE_BOT`). The key of an invitation for a bot is limited to it: valid while it waits, then until the end of its game, and it joins the queue with it.

## State

`Game`, `Player` and `PhysicalCard` implement `State/Model/StatefulInterface`: they carry a JSON `state` field, decoded by the managers in `src/State/Manager` (`GameStateManager`, `PlayerStateManager`, `CardStateManager`) into `GameState` / `PlayerState` / `CardState` (fate on the card, honor tokens on a province or a holding, personal honor, the skills set by the players, the controller when another player has taken control of it). `GameState` also holds the rings (`RingState`: fate, claiming player and the type of the conflict it was claimed in), the Imperial Favor and the conflict being resolved (`ConflictState`: players, contested ring, type, attacked provinces, participating characters by card id) and the duel being resolved (`DuelState`: players, characters involved, step, declared statistics, result). Modify it through `withState(closure)`, which decodes, runs the callback and re-encodes.

## Action pipeline

1. A player action is a Messenger message in `src/Message`, implementing `ActionInterface` (or `PlayerActionInterface` when it has a player) and tagged with `#[AppAction]`, which makes it discoverable by `Service/ActionMessageRegistry`. The attribute says whether players can send it through the API (`public`, false for the platform actions: `CreateGame`, `JoinGame`, and those the engine sends itself: `SetHonor`, the starting honor), and whether it is special (`special`: an effect few cards have, such as `PutCardOnDeck`, `InitiateDuel` or `SwitchRing`, which the web client offers apart; the engine accepts it like any other), and whether it is independent (`independent`: what a player does on their own where the players act at once, never rejected for a stale version, see `GameVersionMiddleware`). Its `playerId` is always the player sending it; the player an effect applies to is a separate field (`targetPlayerId`, or `giverId` / `recipientId` for `TransferHonor`). Messages hold ids (game, player, card) as strings, not entities. The message is the single source of truth of its payload: the values are checked by constraints of the Validator on the arguments of its constructor (`#[Assert\…]`), each field is described by a `#[Description]` attribute and the message by its class doc comment, from which `Service/Api/MessageSchemaFactory` builds the JSON schema of the payload.
2. Its handler in `src/MessageHandler` (`#[AsMessageHandler]`, `final readonly`) loads entities through repositories and changes the state, usually by applying a transition on the relevant workflow. The handler of a public player action implements `MessageHandler/PlayerActionHandlerInterface`: `assertAvailable(Game, Player)` checks what the action requires from the state whatever its payload (game place, active player, duel step…), throwing the same rules exceptions as the rest of the handling; it only reads the state. The handler calls it before handling the message, and `Service/AvailableActionsResolver` calls it to list the actions a player can send now, so that both cannot diverge. `App\Kernel` maps each of these handlers to its message (type of the parameter of `__invoke()`) in a service locator; a test checks that every public message has one.
3. Middlewares (order in `config/packages/messenger.yaml`):
   - `validation`: checks the constraints of the message (`ValidationFailedException`), before any lock or transaction. The handlers only check what needs the state.
   - `GameUpdatedNotificationMiddleware`: once the transaction is committed, notifies the players that the game has changed (`GameUpdatedNotification`: Mercure topic `/games/{id}`, with the new version and no data of the game), and, once the last player has joined (`JoinGame`, the game has started), every player that it has started (`GameStartedNotification`, `game_started` on `/users/{id}`, with the game and the player of each user). Nothing is notified when the handling fails.
   - Doctrine transaction: commits everything at the end.
   - `GameLockMiddleware`: locks the game row (`SELECT … FOR UPDATE`) before the handling, so the actions on a game and the automatic transitions they lead to are handled one at a time. A game already loaded is locked but not reloaded: load nothing of the game before dispatching.
   - `GameVersionMiddleware`: rejects a message sent with an `ExpectedVersionStamp` (`Middleware/Stamp`) once the game has changed (`StaleVersionException`), before its handling, unless the message is independent (`AppAction::$independent`: its handling does not depend on what the other players did since its sender read the game, so that two players acting at once do not reject each other: `RevealDynastyCard`, `ChooseStrongholdProvince`, `BidHonor`, `DeclareConflictSkill`, `DeclareProvinceStrength`, `DeclareGloryCount`, `DeclareDuelStatistic`; the handler still checks the state). The expected version is a stamp, not part of the message, so that replaying an event never fails on it.
   - `GameEndedMiddleware`: rejects any action on a game that has ended (`GameEndedException`), before its handling.
   - `GameReplayMiddleware`: rejects any action on a replay (`ReplayReadOnlyException`) but the events it replays (`ReplayStamp`), whoever sends it.
   - `EventRecordingMiddleware`: once the message and its automatic transitions are handled, increments the version of the game (and sets `updatedAt` from the clock) and saves the message as an `Event` with that version. It comes before `WorkflowTransitionMiddleware`, so that the log entries of the automatic transitions belong to the version of the message that led to them.
   - `WorkflowTransitionMiddleware`: after the handling, repeatedly applies the enabled game transition marked `metadata.auto: true` with the highest `metadata.priority` (0 by default); two enabled automatic transitions sharing the highest priority throw a `LogicException`.
   - `ProvinceRefillMiddleware`: right after the handling, before the automatic transitions, refills the provinces the handlers have scheduled (see `game-flow.md`, "Refilling the provinces").
4. `Service/EventPlayer` deserializes a stored `Event` (or a message name and payload) and re-dispatches it, so a game can be replayed from its event log. Messages must therefore stay serializable.

A handler does what a message does in every place. What depends on the step goes in a listener of a domain event (`src/Event`, named in the past tense: `OpportunityPassedEvent`) dispatched by the handler: the listener (`src/EventListener`, named after the place and the event, e.g. `PlayCardsFromProvincesOpportunityPassedListener`) checks the game place. The event carries the entities and the values its listeners need, computed before the state changes when necessary (`firstToPass`). These events are also the hook for cards reacting to what happens, and the entries of the log of the game (see "Game log"): a change of the state that is not a transition dispatches a domain event. A message that must behave differently in some step is a different message.

## Workflows

Six `state_machine` workflows defined in PHP in `config/packages/workflows.php` (Symfony 7.4 array-shape config, `App::config()`; keys are checked by PHPStan against `config/reference.php`): `game` plus one per card type (e.g. dynasty card: `draw_card`, `turn_faceup`, `turn_facedown`, `play`, `discard`; the role only triggers its abilities, `trigger_ability`). Use the place constants of the card classes and enums in metadata (`StackType::Hand`, `Orientation::FaceUp`), and the helpers of `Workflow/WorkflowConfig` (`transition()`, `cardWorkflow()`, `bowAndReady()`, `triggerAbility()`). Only the `game` places carrying metadata are declared (`places`); the others come from the transitions. Audit trail is on (`workflow` log channel).

**Card place = stack type + orientation.** A card's workflow place is not stored: `PhysicalCard::getCurrentPlace()` computes it with the `getPlace(StackType, Orientation)` mapping of each card class (e.g. a province `UpsideDown` is broken, a dynasty card `FaceUp` in a province is `on_province_faceup`). A place stands for a set of available transitions, so orientations that do not change them share a place: a bowed card (`Sideways`) is still `in_play`, and `bow` / `ready` are transitions from `in_play` to itself. A stack in play is a character (its first card, whatever its printed type: `PhysicalCard::isCharacterInPlay()`) and the cards attached to it (`getAttachedCharacter()`): a printed character attached to another one is `attached` (conflict and dynasty cards), the only place that reads the position of the card in its stack. Only what is not a physical position (honor status, fate tokens…) goes in the card `state`. Card workflows use `Workflow/CardMarkingStore`, which reads that computed place and, after a transition, checks that the card really ended up in the target place.

Card transitions declare their effect in metadata, applied by the generic `Workflow/CardTransitionListener`: `stack` (StackType the card moves to), `orientation` (Orientation it takes; required on a move, otherwise the card keeps its orientation) and `position` (`bottom`: at the bottom of the stack, on top otherwise; a card can move within its stack, e.g. to the bottom of its deck). Target stack: the context `stack` (e.g. the character or province an attachment goes on, possibly an opponent's, a character played as an attachment included); else, entering play, a new stack of its controller for a character or a card the transition turns into one (metadata `character`: `detach`); else the player's unique stack. `CardMarkingStore` rejects a target stack the card cannot be in. Write a specific listener only for what metadata cannot express, like `Workflow/LeavePlayListener` (consequences of any transition out of `in_play` or `attached` but `detach`: personal honor, tokens, control, attachments, conflict participation), `Workflow/HostLeaveListener` (the cards under a card discarded once it leaves its place) or `Workflow/TakeControlListener` (`take_control`: the controller in the context, the character moved with its attachments to a new stack of its controller). Never move or turn a card outside a transition.

The `game` workflow models the round sequence; a new place exists when the phase **and** the available player actions differ. Place metadata:

- `action_window`: players can trigger action abilities (`TriggerActionAbility`) and play cards (`PlayCharacter`, `PlayAttachment`, `PlayActionEvent`); `play_from_hand: false` forbids characters and attachments (1.4), wherever they are played from. `OpportunityService::assertCanTakeAction()` checks it. The `trigger_ability` transition of a card workflow (from a place to itself) lists where the abilities of a card can be used (`TriggerActionAbility`, `TriggerInterruptAbility`, `TriggerReactionAbility`).
- `opportunities`: players have opportunities to act, in player order or simultaneously, and can pass them (`PassOpportunity`); the step ends once every player has passed (`AllPlayersPassedGuardListener`). Its value is an `Enum/PassingRule`: `Final` (passing forfeits the remaining opportunities of the step) or `Consecutive` (action windows: a player who acts cancels the passes, and the window closes once every player has passed consecutively).

Transition metadata: `auto` and `priority` (see `WorkflowTransitionMiddleware`), and `log`, the template of the entry the transition writes in the log of the game (required on every transition of every workflow, see "Game log"). `end_game` leads from every place of a started game (`WorkflowConfig::placesOf()`) to the final place `game_ended` (`Game::STATE_ENDED`); it is automatic with the highest priority, so the game ends as soon as a player meets a victory condition, before any other automatic transition.

Behaviour lives in listeners under `src/Workflow/<WorkflowName>/`, named after the transition/place and the event type: `...GuardListener` (blocks a transition until conditions are met), `...TransitionListener`, `...EnterListener`.

## Game log

Every change of the state of a game writes an entry in its log (`GameLogEntry`): a template in English whose placeholders (`{player} loses {amount} honor`) are replaced by its params, so that the log can be read as is and translated by the client. The entry belongs to the version of the game the message being handled leads to, automatic transitions included; a message writes any number of entries, ordered by id. The log is written by `GameLog/GameLogger`, from three sources:

- **Card transitions**: `GameLog/CardTransitionLogListener` writes the `log` metadata of the transition, when the card leaves its place (before the consequences of the transition), with the params `card`, `owner`, `from` and `to` (stacks), and `host` (the card it goes under) for an `Underneath` stack.
- **Game transitions**: `GameLog/GameTransitionLogListener` writes the `log` metadata of the transition (no params), before its listeners.
- **Domain events**: a domain event of `src/Event` carrying the `#[GameLog('template')]` attribute (and implementing `Event/GameEventInterface`) writes its entry when it is dispatched, before its other listeners (`GameLog/GameLogEventListener`, registered by `App\Kernel` for every such event); the placeholders name its properties, and `params` the properties stored without being shown, for the clients (`DeckSearchedEvent`: the cards of a deck searched, which the window of the searcher shows and the log does not list). Every change of the state that is not a transition dispatches one. Bookkeeping that follows from a logged transition is not logged: active players and passes reset when a step begins, turn records, honor dials reset, conflict and duel cleanup.

The log tells *what* changed, not why (the engine does not know the card effects); the client gets the type and the sender of each message beside its entries.

**Visibility of the params** (`GameLog/LogParam`): a param is `player`, `card`, `stack`, `ring`, `value` or `list`. A card or a value may be known to some players only: its visibility is null when public, else the list of the ids of the players who know it (empty: nobody). It is computed when the entry is written, from the state: a card is known to the players who see it before or after the transition (`View/Visibility`: its id when they see its stack, its code when they see its face), a property of an event marked `#[VisibleTo('player')]` only to that player (`#[VisibleTo]`: nobody), a card marked `#[Revealed]` to every player. `View/GameLogViewFactory` masks the log for each reader: a hidden card has no id nor code (no code when only its id is known), a hidden value has `hidden: true`; a reader who is not a player (spectators, to come) only sees what is public.

## Exceptions

`Exception/Data` (missing/mismatched data) vs `Exception/Rules` (game-rule violations).
