# L5R Game Engine

Server-side engine to play **Legend of the Five Rings LCG** (Fantasy Flight Games). PHP 8.4, Symfony 7.4, Doctrine ORM on PostgreSQL, Symfony Messenger, Symfony Workflow, Mercure.

## MVP scope

- The engine acts as a **board**: it enforces the game flow (rounds, phases, framework steps) but **does not enforce card rules**.
- Only the **Stronghold format** (two players) is in scope.

The state of the implementation and the open points are listed in `HANDOFF.md`.

## Architecture

### Domain model (`src/Entity`)

- `LogicalCard`: the card as printed (title, cost, text), grouped in `Pack` via `Printing`. `abilityTimings` lists the timings of its triggered abilities (`Enum/AbilityTiming`: action, interrupt, reaction), and `abilityGrantedToAttached` flags the attachments whose abilities belong to the card they are attached to ("Attached character gains…"); both are stored in the card fixtures.
- `PhysicalCard`: one copy of a card in a game, owned by a `Player`. Mapped superclass with one subclass per type in `src/Entity/CardTypes` (Conflict, Dynasty, Province, Role, Stronghold).
- `Stack`: ordered collection of physical cards (deck, hand, province, etc.; see `Enum/StackType`). The top card has the highest `position`. When order matters, use `getOrderedCards()` / `getTopCards()`: the order of `getCards()` is not kept in sync with positions (e.g. after `moveCard()`).
- Shuffling (`Service/StackShuffler`, never `Randomizer::shuffleArray()` on cards directly) makes the players lose track of the cards: it deletes them and creates them again in random order with new ids (same logical card, player, stack and orientation, fresh state), so that an id seen before cannot be followed into a shuffled deck. Code holding a card of a stack across a shuffle must read it again from the stack.
- `Enum/Orientation`: physical orientation of a card (`FaceDown`, `FaceUp`, `Sideways`, `UpsideDown`), stored on `PhysicalCard`. A new card takes the initial orientation of its class (`getInitialOrientation()`: face down, except stronghold and role); afterwards only workflow transitions change it.
- `Game`: carries a `version`, the number of messages handled on it (incremented with each `Event`, so that the events of a game are numbered from 1), and its own random generator (`getRandomizer()`, seeded by `CreateGame::seed`, engine state saved with the game) for every random draw (shuffles, first player, random discards, ids of the cards and stacks it creates: `generateId()`), so that replaying the event log gives the same game. Never draw outside of it.
- `Deck`: quantity by card code; each copy becomes a physical card when a game starts (`Deck::getCardCodes()`). A deck belongs to the user who imported it; a deck without owner (the starter decks of the fixtures) can be used by every user.
- `ExternalCard`: links the id of a card in an external database (`Enum/CardSource`, e.g. EmeraldDB) to a `LogicalCard`, to import the decks built there; loaded from `fixtures/external_cards/<source>.json` (card code by external id).
- `Event`: persisted record of every handled action, numbered by the version of its game. It holds the payload of the message, secret information included (the seed of `CreateGame`, secret bids…): it is never shown to the players, who read the log of the game (see below).
- `GameLogEntry`: a line of the log of a game, what changed in it (see "Game log").
- `Candidate`: a player waiting in the matchmaking queue.
- `User`: an account, human or bot (`Enum/UserType`); a bot is owned by a human. Its id is its user identifier. A `Player` and a `Candidate` belong to a user (`Player::getUserId()` reads the id without loading the user); a user is a candidate at most once. `AccessToken`: a token of a user, stored as its SHA-256 hash, either a session or an API key (`Enum/AccessTokenType`); only a bot gets API keys, so that a program playing through one is known as a bot (`ROLE_BOT`).

### State

`Game`, `Player` and `PhysicalCard` implement `State/Model/StatefulInterface`: they carry a JSON `state` field, decoded by the managers in `src/State/Manager` (`GameStateManager`, `PlayerStateManager`, `CardStateManager`) into `GameState` / `PlayerState` / `CardState` (fate on the card). `GameState` also holds the rings (`RingState`: fate, claiming player), the Imperial Favor and the conflict being resolved (`ConflictState`: players, contested ring, type, attacked provinces, participating characters by card id) and the duel being resolved (`DuelState`: players, characters involved, step, declared statistics, result). Modify it through `withState(closure)`, which decodes, runs the callback and re-encodes.

### Action pipeline

1. A player action is a Messenger message in `src/Message`, implementing `ActionInterface` (or `PlayerActionInterface` when it has a player) and tagged with `#[AppAction]`, which makes it discoverable by `Service/ActionMessageRegistry`. The attribute says whether players can send it through the API (`public`, false for the platform actions: `CreateGame`, `JoinGame`) Its `playerId` is always the player sending it; the player an effect applies to is a separate field (`targetPlayerId`, or `giverId` / `recipientId` for `TransferHonor`). Messages hold ids (game, player, card) as strings, not entities. The message is the single source of truth of its payload: the values are checked by constraints of the Validator on the arguments of its constructor (`#[Assert\…]`), each field is described by a `#[Description]` attribute and the message by its class doc comment, from which `Service/Api/MessageSchemaFactory` builds the JSON schema of the payload.
2. Its handler in `src/MessageHandler` (`#[AsMessageHandler]`, `final readonly`) loads entities through repositories and changes the state, usually by applying a transition on the relevant workflow. The handler of a public player action implements `MessageHandler/PlayerActionHandlerInterface`: `assertAvailable(Game, Player)` checks what the action requires from the state whatever its payload (game place, active player, duel step…), throwing the same rules exceptions as the rest of the handling; it only reads the state. The handler calls it before handling the message, and `Service/AvailableActionsResolver` calls it to list the actions a player can send now, so that both cannot diverge. `App\Kernel` maps each of these handlers to its message (type of the parameter of `__invoke()`) in a service locator; a test checks that every public message has one.
3. Middlewares (order in `config/packages/messenger.yaml`):
   - `validation`: checks the constraints of the message (`ValidationFailedException`), before any lock or transaction. The handlers only check what needs the state.
   - `GameUpdatedNotificationMiddleware`: once the transaction is committed, notifies the players that the game has changed (`GameUpdatedNotification`: Mercure topic `/games/{id}`, with the new version and no data of the game). Nothing is notified when the handling fails.
   - Doctrine transaction: commits everything at the end.
   - `GameLockMiddleware`: locks the game row (`SELECT … FOR UPDATE`) before the handling, so the actions on a game and the automatic transitions they lead to are handled one at a time. A game already loaded is locked but not reloaded: load nothing of the game before dispatching.
   - `GameVersionMiddleware`: rejects a message sent with an `ExpectedVersionStamp` (`Middleware/Stamp`) once the game has changed (`StaleVersionException`), before its handling. The expected version is a stamp, not part of the message, so that replaying an event never fails on it.
   - `GameEndedMiddleware`: rejects any action on a game that has ended (`GameEndedException`), before its handling.
   - `EventRecordingMiddleware`: once the message and its automatic transitions are handled, increments the version of the game and saves the message as an `Event` with that version. It comes before `WorkflowTransitionMiddleware`, so that the log entries of the automatic transitions belong to the version of the message that led to them.
   - `WorkflowTransitionMiddleware`: after the handling, repeatedly applies the enabled game transition marked `metadata.auto: true` with the highest `metadata.priority` (0 by default); two enabled automatic transitions sharing the highest priority throw a `LogicException`.
4. `Service/EventPlayer` deserializes a stored `Event` (or a message name and payload) and re-dispatches it, so a game can be replayed from its event log. Messages must therefore stay serializable.

A handler does what a message does in every place. What depends on the step goes in a listener of a domain event (`src/Event`, named in the past tense: `OpportunityPassedEvent`) dispatched by the handler: the listener (`src/EventListener`, named after the place and the event, e.g. `PlayCardsFromProvincesOpportunityPassedListener`) checks the game place. The event carries the entities and the values its listeners need, computed before the state changes when necessary (`firstToPass`). These events are also the hook for cards reacting to what happens, and the entries of the log of the game (see "Game log"): a change of the state that is not a transition dispatches a domain event. A message that must behave differently in some step is a different message.

HTTP API (access token: `Authorization: Bearer <token>`, see "Other services" for authentication):

- `POST /api/games/{id}/messages` (`ApiGameMessagesController`): a player of the game sends any public action message, `{"type": "pass_opportunity", "payload": {...}}`. The type is the snake case short name of the message class; the payload holds its constructor arguments in snake case (serializer name converter). `Service/Api/ApiMessageFactory` builds the message: the game comes from the URL, the player (sender) is the authenticated player (the payload cannot hold `game_id` nor `player_id`); the target of an effect is in the payload (`target_player_id`…). The controller only reads ids before dispatching (see `GameLockMiddleware`). Versions: the `ETag` of the response is the version of the game once the message is handled (`"12"`); with `If-Match` (a single ETag of the game, or `*`), the message is rejected with a 412 (`stale_version`) if the game has changed since. Responses: 204 once handled; errors are problem details (`application/problem+json`, `type` from the exception): 400 invalid body, type, payload (`invalid_payload`: structure of the payload, with `violations`) or `If-Match` (`invalid_if_match`); 401 no token; 403 not a player of the game; 404 unknown game; 409 forbidden by the rules in the current state (`Exception/Rules`, `WorkflowException`, workflow transition not enabled); 412 stale version; 422 payload referring to nothing in the game or with invalid values (`validation_failed`: constraints of the message, with `violations`). A violation has a `property_path` (snake case) and a `message`.
- `GET /api/actions` (`ApiActionsController`): the catalogue of the public messages, the JSON schema of the payload of each type (`MessageSchemaFactory`). Public (no token) and cacheable. The schemas are also committed in `schemas/messages` (`bin/console app:message-schemas:dump`), the snapshot of the contract of the API: a test fails when they differ from the messages.
- `GET /api/games/{id}` (`ApiGamesController`): the state of the game as the authenticated player sees it, built by `View/GameViewFactory::create(Game, Player $viewer)` into the readonly DTOs of `View/Model` (`GameView`, `PlayerView`, `StackView`, `CardView`) and serialized in snake case. A read goes neither through the bus nor through `GameLockMiddleware`. Same errors as the messages API (401, 403, 404). The `ETag` is the version of the game (also `version` in the view): the view only depends on the state and the viewer, so a player sending the ETag they have (`If-None-Match`) gets a 304 until the game changes; the response is `private, no-cache`. The visibility rules only depend on the state, never on the game place, and those of the cards are written once, in `View/Visibility` (shared with the log): decks and the opponents' hands are sent as counts (`cards: null`), a face-down card has no `code` (except a province for its owner); the secret information of `PlayerState` (`pendingHonorBid`, `strongholdProvinceId`) goes to its owner only (in the factory); everything else is public. Cards are sent by code: the client reads them from `GET /api/cards`. New secret information must be stored apart from what is public, and masked in the factory. `available_actions` lists the types of the public messages the viewer can send now (`AvailableActionsResolver`, none once the game has ended): an action is listed when its handler's `assertAvailable()` passes, its payload can still be rejected.
- `GET /api/cards` and `GET /api/cards/{code}` (`ApiCardsController`): the cards as printed (`LogicalCard`), every card sorted by code or one card, built by `View/LogicalCardViewFactory` into `View/Model/LogicalCardView` (code, printed attributes, `ability_timings`, `ability_granted_to_attached`; not the packs), serialized in snake case. Public (no token) and cacheable, like `GET /api/actions`; 404 `card_not_found` for an unknown code.
- `GET /api/self` (`ApiSelfController`): the identifier of the authenticated user. `GET /api/self/games`: their games, in progress or ended, the last joined first (`View/Model/UserGameView`: id, their `player_id`, `version`, `ended`, the users in player order), so that a user matched by the queue finds their game (`GameRepository::findByUser()`, a single query).
- `GET /api/decks`, `GET /api/decks/{id}` and `POST /api/decks` (`ApiDecksController`): the decks the authenticated user can use (their own and the starter decks; the others are not found, 404 `deck_not_found`), and the import of a deck: `{"name": ..., "format": "emeralddb", "cards": {"<card id>": <quantity>}}`, 201 with the deck (`View/Model/DeckView`). `Service/Deck/DeckImporter` converts the ids of the format to codes (`Service/Deck/DeckFormatInterface`, one tagged service per format: `codes` for the codes of the engine, `emeralddb` through the external cards), then checks the deckbuilding rules of the Stronghold format (`Service/Deck/DeckConstructionValidator`, not the banned and restricted lists). Errors: 400 `invalid_payload` (structure, with `violations`), 422 `invalid_deck` (unknown format, card unknown to the format, broken rule; `violations` on `format`, `cards[<id>]` or `cards`).
- `GET`, `POST` and `DELETE /api/queue` (`ApiQueueController`): the matchmaking queue. A user joins it with a deck they can use (`{"deck_id": ...}`, 204; 409 `already_queued`, 422 `deck_not_found`) and is matched at once when another candidate waits; `GET` gives the deck they wait with (404 `not_queued` once matched or left).
- `GET /api/games/{id}/log?since={version}` (`ApiGamesController`): the log of the game after a version (0 by default) as the authenticated player reads it (`View/GameLogViewFactory`): the messages handled on the game (`version`, `type`, sender `player_id`, never the payload), each with its entries (`template`, `params`) masked for the reader. Same errors and `ETag` as the view, 400 `invalid_since`.
- Console commands (`src/Command`) drive the rest of the engine; `app:game:log <id> [--as=<user>]` shows the log as a player (or a spectator) reads it.

### Workflows

Six `state_machine` workflows defined in PHP in `config/packages/workflows.php` (Symfony 7.4 array-shape config, `App::config()`; keys are checked by PHPStan against `config/reference.php`): `game` plus one per card type (e.g. dynasty card: `draw_card`, `turn_faceup`, `turn_facedown`, `play`, `discard`). Use the place constants of the card classes and enums in metadata (`StackType::Hand`, `Orientation::FaceUp`), and the helpers of `Workflow/WorkflowConfig` (`transition()`, `cardWorkflow()`, `bowAndReady()`, `triggerAbility()`). Only the `game` places carrying metadata are declared (`places`); the others come from the transitions. Audit trail is on (`workflow` log channel).

**Card place = stack type + orientation.** A card's workflow place is not stored: `PhysicalCard::getCurrentPlace()` computes it with the `getPlace(StackType, Orientation)` mapping of each card class (e.g. a province `UpsideDown` is broken, a dynasty card `FaceUp` in a province is `on_province_faceup`). A place stands for a set of available transitions, so orientations that do not change them share a place: a bowed card (`Sideways`) is still `in_play`, and `bow` / `ready` are transitions from `in_play` to itself. Only what is not a physical position (honor status, fate tokens…) goes in the card `state`. Card workflows use `Workflow/CardMarkingStore`, which reads that computed place and, after a transition, checks that the card really ended up in the target place.

Card transitions declare their effect in metadata, applied by the generic `Workflow/CardTransitionListener`: `stack` (StackType the card moves to) and `orientation` (Orientation it takes; required on a move, otherwise the card keeps its orientation). Target stack: a character entering play gets a new stack (`PhysicalCard::entersPlayInNewStack()`); otherwise the context `stack` (e.g. the character or province an attachment goes on, possibly an opponent's), else the player's unique stack. `CardMarkingStore` rejects a target stack the card cannot be in. Write a specific listener only for what metadata cannot express, like `Workflow/LeavePlayListener` (consequences of any transition out of `in_play`: personal honor, tokens, attachments, conflict participation). Never move or turn a card outside a transition.

The `game` workflow models the round sequence; a new place exists when the phase **and** the available player actions differ. Place metadata:

- `action_window`: players can trigger action abilities (`TriggerActionAbility`) and play cards from hand (`PlayCharacterFromHand`, `PlayAttachment`, `PlayActionEvent`); `play_from_hand: false` forbids characters and attachments from hand (1.4). `OpportunityService::assertCanTakeAction()` checks it. The `trigger_ability` transition of a card workflow (from a place to itself) lists where the abilities of a card can be used (`TriggerActionAbility`, `TriggerInterruptAbility`, `TriggerReactionAbility`).
- `opportunities`: players have opportunities to act, in player order or simultaneously, and can pass them (`PassOpportunity`); the step ends once every player has passed (`AllPlayersPassedGuardListener`). Its value is an `Enum/PassingRule`: `Final` (passing forfeits the remaining opportunities of the step) or `Consecutive` (action windows: a player who acts cancels the passes, and the window closes once every player has passed consecutively).

Transition metadata: `auto` and `priority` (see `WorkflowTransitionMiddleware`), and `log`, the template of the entry the transition writes in the log of the game (required on every transition of every workflow, see "Game log"). `end_game` leads from every place of a started game (`WorkflowConfig::placesOf()`) to the final place `game_ended` (`Game::STATE_ENDED`); it is automatic with the highest priority, so the game ends as soon as a player meets a victory condition, before any other automatic transition.

Behaviour lives in listeners under `src/Workflow/<WorkflowName>/`, named after the transition/place and the event type: `...GuardListener` (blocks a transition until conditions are met), `...TransitionListener`, `...EnterListener`.

### Game flow

- **Values from players**: since the engine does not apply card effects, a step whose outcome cards can modify (e.g. the amount of fate collected) is a player action carrying the value; an `auto` transition guarded on every player having acted then moves the game on.
- **Turn records**: what a player did during the round goes in the turn records of `PlayerState`, reset at the end of the round (`fate_phase_ended`).
- **Player order**: stored in `GameState` (`playerIds`, fixed by `start_game` from the order of arrival, `Player::joinRank`; the first player changes, not the order).
- **Opportunities to act**: the players who have the opportunity to act are the active players of `GameState` (`activePlayerIds`); the handler of each action rejects a player who is not active (`NotActivePlayerException`). The enter listener of the step activates them (`FirstPlayerOpportunityEnterListener` and `AllPlayersOpportunityEnterListener` cover the common cases):
  - in steps resolved in player order, only the first player: the handler gives the opportunity to act to the next player (`GameState::getNextPlayerId()` / `getPlayerIdsAfter()`, resolved with `Game::getPlayer()`). An action that requires follow-up actions keeps the opportunity with the player, who ends it with `EndOpportunity`;
  - in steps where players act simultaneously (e.g. `reveal_honor_dials`, the `react_to_*` reaction windows of a conflict), every player: they keep their opportunity until they pass (`EndOpportunity` changes nothing).

  A player who passes (`PassOpportunity`, in a place marked `opportunities`; `PlayerState::passed`, reset by the enter listener of the step) is no longer active and is skipped by `Service/OpportunityService`. In an action window (`PassingRule::Consecutive`), a player who ends an opportunity in which they acted (`EndOpportunity`) resets every pass, so the players who had passed get opportunities to act again.
- **End of the game**: `Service/VictoryService` checks the victory conditions from the state (a player with 25 or more honor wins; a player with no honor is eliminated and the last one standing wins; ties go to the first player, then in player order). The guard of `end_game` uses it, and its transition listener records `winnerId` and `victoryCondition` in `GameState`. Honor cannot go below 0 (`PlayerState::setHonor()`).
- **Duels**: a duel is not a place of the `game` workflow, since it returns to the action window it was initiated in: it is the `DuelState` of `GameState`, whose steps the messages move on (`InitiateDuel`, `BidHonor`, `DeclareDuelStatistic`, `EndDuel`). While a duel is being resolved, no action window is open and the players cannot pass or end their opportunity (`OpportunityService::assertNoDuel()`).
- **Interrupts and reactions** are initiated when their triggering condition occurs, not during an opportunity to act: `PlayInterruptEvent`, `PlayReactionEvent`, `TriggerInterruptAbility` and `TriggerReactionAbility` are accepted from any player in any place, during a duel too, and change no opportunity. Action events and abilities (`PlayActionEvent`, `TriggerActionAbility`) require the opportunity to act in an action window. An event is played with the message of its timing (`AbilityTiming`), and its message is available only with such an event in hand; the abilities of cards are not checked against their timings, since cards gain and lose abilities.
- **Secret information**: what a player knows and their opponents do not is stored apart from what is public, so that its visibility only depends on the state (e.g. `PlayerState::pendingHonorBid`, the secret bid, and `honorBid`, the revealed one).
- **Costs and effects**: board manipulations (`BowCard`, `LoseHonor`, `DiscardCard`, `HonorCharacter`, `MoveToConflict`…) are accepted in any place, from any player of the game, on any card or player, since the engine does not know which ability is being resolved.
- **Totals from players**: the engine does not compute skills, province strengths or glory, which card effects modify: players declare them (`DeclareConflictSkill`, `DeclareProvinceStrength`, `DeclareGloryCount`) and the engine applies the rules to the declared values (winner, broken provinces, Imperial Favor).

### Game log

Every change of the state of a game writes an entry in its log (`GameLogEntry`): a template in English whose placeholders (`{player} loses {amount} honor`) are replaced by its params, so that the log can be read as is and translated by the client. The entry belongs to the version of the game the message being handled leads to, automatic transitions included; a message writes any number of entries, ordered by id. The log is written by `GameLog/GameLogger`, from three sources:

- **Card transitions**: `GameLog/CardTransitionLogListener` writes the `log` metadata of the transition, when the card leaves its place (before the consequences of the transition), with the params `card`, `owner`, `from` and `to` (stacks).
- **Game transitions**: `GameLog/GameTransitionLogListener` writes the `log` metadata of the transition (no params), before its listeners.
- **Domain events**: a domain event of `src/Event` carrying the `#[GameLog('template')]` attribute (and implementing `Event/GameEventInterface`) writes its entry when it is dispatched, before its other listeners (`GameLog/GameLogEventListener`, registered by `App\Kernel` for every such event); the placeholders name its properties. Every change of the state that is not a transition dispatches one. Bookkeeping that follows from a logged transition is not logged: active players and passes reset when a step begins, turn records, honor dials reset, conflict and duel cleanup.

The log tells *what* changed, not why (the engine does not know the card effects); the client gets the type and the sender of each message beside its entries.

**Visibility of the params** (`GameLog/LogParam`): a param is `player`, `card`, `stack`, `ring`, `value` or `list`. A card or a value may be known to some players only: its visibility is null when public, else the list of the ids of the players who know it (empty: nobody). It is computed when the entry is written, from the state: a card is known to the players who see it before or after the transition (`View/Visibility`: its id when they see its stack, its code when they see its face), a property of an event marked `#[VisibleTo('player')]` only to that player (`#[VisibleTo]`: nobody), a card marked `#[Revealed]` to every player. `View/GameLogViewFactory` masks the log for each reader: a hidden card has no id nor code (no code when only its id is known), a hidden value has `hidden: true`; a reader who is not a player (spectators, to come) only sees what is public.

### Other services

- Matchmaking: `Service/MatchMaking/FifoMatchMakingService` pairs the candidates in their order of arrival, holding the lock of the queue (`CandidateRepository::withQueueLock()`, a PostgreSQL advisory lock); `Service/GameLauncher/AutomaticGameLauncher` creates the game through the bus (`CreateGame`, then `JoinGame` for each candidate: recorded as events, the game starts once both have joined) and removes the candidates. It runs when a user joins the queue, or with `app:matchmaking`.
- Notifications: `NotificationInterface` objects sent through `NotifierInterface`; `MercureNotifier` publishes server-sent events, `LoggerNotifier` logs them.
- Security: stateless access-token authentication, no password: `Security/AccessTokenHandler` finds the `AccessToken` by the hash of the token, with its `User` (a single query; an unknown token gets a 401). A user is matched to the player of a game through `Player::user`. `Security/AccessTokenIssuer` issues the tokens (random, prefixed `l5r_`, returned once). The API issues none yet: users and tokens are created by console commands (`app:user:create`, `app:token:create`, `app:token:revoke`), and the fixtures hold users with known tokens (`DataFixtures/UserFixtures`, in clear, development and tests only).
- Mercure: the topic `/games/{id}` is public; it carries no data of the game, only its id and version.
- Exceptions: `Exception/Data` (missing/mismatched data) vs `Exception/Rules` (game-rule violations).
