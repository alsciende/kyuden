# Kyūden

[kyuden.app](https://kyuden.app): server-side engine to play **Legend of the Five Rings LCG** (Fantasy Flight Games). PHP 8.4 (PHP-FPM behind nginx in development), Symfony 7.4, Doctrine ORM on PostgreSQL, Symfony Messenger, Symfony Workflow, Mercure; and its web client (`front/`): Vue 3, Vite, TypeScript.

## Installation

You need git, make and Docker.

```shell
git clone <this repo>
cd kyuden
make build
make up
make install
make db
make front-install
open http://localhost:8080
```

## MVP scope

- The engine acts as a **board**: it enforces the game flow (rounds, phases, framework steps) but **does not enforce card rules**.
- Only the **Stronghold format** (two players) is in scope.

The state of the implementation and the open points are listed in `HANDOFF.md`.

## Architecture

### Domain model (`src/Entity`)

- `LogicalCard`: the card as printed (title, cost, text), grouped in `Pack` via `Printing`. `abilityTimings` lists the timings of its triggered abilities (`Enum/AbilityTiming`: action, interrupt, reaction), and `abilityGrantedToAttached` flags the attachments whose abilities belong to the card they are attached to ("Attached character gains…"); both are stored in the card fixtures.
- `PhysicalCard`: one copy of a card in a game, owned by a `Player`. Mapped superclass with one subclass per type in `src/Entity/CardTypes` (Conflict, Dynasty, Province, Role, Stronghold).
- `Stack`: ordered collection of physical cards (deck, hand, province, etc.; see `Enum/StackType`). The top card has the highest `position`. When order matters, use `getOrderedCards()` / `getTopCards()`: the order of `getCards()` is not kept in sync with positions (e.g. after `moveCard()`).
- Shuffling (`Service/StackShuffler`, never `Randomizer::shuffleArray()` on cards directly) makes the players lose track of the cards: it deletes them and creates them again in random order with new ids (same logical card, player, stack and orientation, fresh state), so that an id seen before cannot be followed into a shuffled deck. Code holding a card of a stack across a shuffle must read it again from the stack.
- `Enum/Orientation`: physical orientation of a card (`FaceDown`, `FaceUp`, `Sideways`, `UpsideDown`), stored on `PhysicalCard`. A new card takes the initial orientation of its class (`getInitialOrientation()`: face down, except stronghold and role); afterwards only workflow transitions change it.
- `Game`: carries a `version`, the number of messages handled on it (incremented with each `Event`, so that the events of a game are numbered from 1), and its own random generator (`getRandomizer()`, seeded by `CreateGame::seed`, engine state saved with the game) for every random draw (shuffles, first player, random discards, ids of the cards and stacks it creates: `generateId()`), so that replaying the event log gives the same game. Never draw outside of it.
- `Deck`: quantity by card code; each copy becomes a physical card when a game starts (`Deck::getCardCodes()`). A deck belongs to the user who imported it; a deck without owner (the starter decks of the fixtures) can be used by every user. An account gets its own copy of the starter deck of its preferred clan when it is created (`Service/Deck/StarterDeckCopier`).
- `ExternalCard`: links the id of a card in an external database (`Enum/CardSource`, e.g. EmeraldDB) to a `LogicalCard`, to import the decks built there; loaded from `fixtures/external_cards/<source>.json` (card code by external id).
- `Event`: persisted record of every handled action, numbered by the version of its game. It holds the payload of the message, secret information included (the seed of `CreateGame`, secret bids…): it is never shown to the players, who read the log of the game (see below).
- `GameLogEntry`: a line of the log of a game, what changed in it (see "Game log").
- `Candidate`: a player waiting in the matchmaking queue.
- `User`: an account, human or bot (`Enum/UserType`); a bot is owned by a human. Its id is its user identifier (a UUID, except the users of the fixtures). Its `name` is its name at court, what the other players see (not unique). A human signs in with a `username` (`[A-Za-z0-9_]{3,32}`, unique whatever its case: `usernameCanonical`) and a password (8 to 4096 characters, hashed by the `auto` hasher of Symfony); a human without a username is a guest (`isGuest()`), who becomes an account by registering (`register()`, `Security/AccountRegistrar`): the same user, so their games, decks and tokens stay theirs. An account has a preferred clan (`preferredClan`, one of the Great Clans: `Enum/Clan::greatClans()`), chosen when it is created and changed at any time; null for a guest or a bot. A user has settings (`settings`, JSON read through `Model/UserSettings`: a missing setting takes its default), for now how the web client draws the cards (`cardDisplay`, `Enum/CardDisplay`: `drawn` or `images`) and whether it is light or dark (`theme`, `Enum/Theme`: `auto`, `light` or `dark`). A `Player` and a `Candidate` belong to a user (`Player::getUserId()` reads the id without loading the user); a user is a candidate at most once. `AccessToken`: a token of a user, stored as its SHA-256 hash, either a session or an API key (`Enum/AccessTokenType`); only a bot gets API keys, so that a program playing through one is known as a bot (`ROLE_BOT`).

### State

`Game`, `Player` and `PhysicalCard` implement `State/Model/StatefulInterface`: they carry a JSON `state` field, decoded by the managers in `src/State/Manager` (`GameStateManager`, `PlayerStateManager`, `CardStateManager`) into `GameState` / `PlayerState` / `CardState` (fate on the card, personal honor, the skills set by the players). `GameState` also holds the rings (`RingState`: fate, claiming player), the Imperial Favor and the conflict being resolved (`ConflictState`: players, contested ring, type, attacked provinces, participating characters by card id) and the duel being resolved (`DuelState`: players, characters involved, step, declared statistics, result). Modify it through `withState(closure)`, which decodes, runs the callback and re-encodes.

### Action pipeline

1. A player action is a Messenger message in `src/Message`, implementing `ActionInterface` (or `PlayerActionInterface` when it has a player) and tagged with `#[AppAction]`, which makes it discoverable by `Service/ActionMessageRegistry`. The attribute says whether players can send it through the API (`public`, false for the platform actions: `CreateGame`, `JoinGame`) Its `playerId` is always the player sending it; the player an effect applies to is a separate field (`targetPlayerId`, or `giverId` / `recipientId` for `TransferHonor`). Messages hold ids (game, player, card) as strings, not entities. The message is the single source of truth of its payload: the values are checked by constraints of the Validator on the arguments of its constructor (`#[Assert\…]`), each field is described by a `#[Description]` attribute and the message by its class doc comment, from which `Service/Api/MessageSchemaFactory` builds the JSON schema of the payload.
2. Its handler in `src/MessageHandler` (`#[AsMessageHandler]`, `final readonly`) loads entities through repositories and changes the state, usually by applying a transition on the relevant workflow. The handler of a public player action implements `MessageHandler/PlayerActionHandlerInterface`: `assertAvailable(Game, Player)` checks what the action requires from the state whatever its payload (game place, active player, duel step…), throwing the same rules exceptions as the rest of the handling; it only reads the state. The handler calls it before handling the message, and `Service/AvailableActionsResolver` calls it to list the actions a player can send now, so that both cannot diverge. `App\Kernel` maps each of these handlers to its message (type of the parameter of `__invoke()`) in a service locator; a test checks that every public message has one.
3. Middlewares (order in `config/packages/messenger.yaml`):
   - `validation`: checks the constraints of the message (`ValidationFailedException`), before any lock or transaction. The handlers only check what needs the state.
   - `GameUpdatedNotificationMiddleware`: once the transaction is committed, notifies the players that the game has changed (`GameUpdatedNotification`: Mercure topic `/games/{id}`, with the new version and no data of the game), and, once the last player has joined (`JoinGame`, the game has started), every player that it has started (`GameStartedNotification`, `game_started` on `/users/{id}`, with the game and the player of each user). Nothing is notified when the handling fails.
   - Doctrine transaction: commits everything at the end.
   - `GameLockMiddleware`: locks the game row (`SELECT … FOR UPDATE`) before the handling, so the actions on a game and the automatic transitions they lead to are handled one at a time. A game already loaded is locked but not reloaded: load nothing of the game before dispatching.
   - `GameVersionMiddleware`: rejects a message sent with an `ExpectedVersionStamp` (`Middleware/Stamp`) once the game has changed (`StaleVersionException`), before its handling. The expected version is a stamp, not part of the message, so that replaying an event never fails on it.
   - `GameEndedMiddleware`: rejects any action on a game that has ended (`GameEndedException`), before its handling.
   - `EventRecordingMiddleware`: once the message and its automatic transitions are handled, increments the version of the game and saves the message as an `Event` with that version. It comes before `WorkflowTransitionMiddleware`, so that the log entries of the automatic transitions belong to the version of the message that led to them.
   - `WorkflowTransitionMiddleware`: after the handling, repeatedly applies the enabled game transition marked `metadata.auto: true` with the highest `metadata.priority` (0 by default); two enabled automatic transitions sharing the highest priority throw a `LogicException`.
4. `Service/EventPlayer` deserializes a stored `Event` (or a message name and payload) and re-dispatches it, so a game can be replayed from its event log. Messages must therefore stay serializable.

A handler does what a message does in every place. What depends on the step goes in a listener of a domain event (`src/Event`, named in the past tense: `OpportunityPassedEvent`) dispatched by the handler: the listener (`src/EventListener`, named after the place and the event, e.g. `PlayCardsFromProvincesOpportunityPassedListener`) checks the game place. The event carries the entities and the values its listeners need, computed before the state changes when necessary (`firstToPass`). These events are also the hook for cards reacting to what happens, and the entries of the log of the game (see "Game log"): a change of the state that is not a transition dispatches a domain event. A message that must behave differently in some step is a different message.

HTTP API (access token: `Authorization: Bearer <token>`, see "Other services" for authentication):

- `POST /api/games/{id}/messages` (`ApiGameMessagesController`, through `Service/Api/PlayerMessageSender`, shared with the MCP tools: checks, dispatch and the problem of a rejected message, `ApiProblemException`): a player of the game sends any public action message, `{"type": "pass_opportunity", "payload": {...}}`. The type is the snake case short name of the message class; the payload holds its constructor arguments in snake case (serializer name converter). `Service/Api/ApiMessageFactory` builds the message: the game comes from the URL, the player (sender) is the authenticated player (the payload cannot hold `game_id` nor `player_id`); the target of an effect is in the payload (`target_player_id`…). The controller only reads ids before dispatching (see `GameLockMiddleware`). Versions: the `ETag` of the response is the version of the game once the message is handled (`"12"`); with `If-Match` (a single ETag of the game, or `*`), the message is rejected with a 412 (`stale_version`) if the game has changed since. Responses: 204 once handled; errors are problem details (`application/problem+json`, `type` from the exception): 400 invalid body, type, payload (`invalid_payload`: structure of the payload, with `violations`) or `If-Match` (`invalid_if_match`); 401 no token; 403 not a player of the game; 404 unknown game; 409 forbidden by the rules in the current state (`Exception/Rules`, `WorkflowException`, workflow transition not enabled); 412 stale version; 422 payload referring to nothing in the game or with invalid values (`validation_failed`: constraints of the message, with `violations`). A violation has a `property_path` (snake case) and a `message`.
- `GET /api/actions` (`ApiActionsController`): the catalogue of the public messages, the JSON schema of the payload of each type (`MessageSchemaFactory`). Public (no token) and cacheable. The schemas are also committed in `schemas/messages` (`bin/console app:message-schemas:dump`), the snapshot of the contract of the API: a test fails when they differ from the messages.
- `GET /api/games/{id}` (`ApiGamesController`): the state of the game as the authenticated player sees it (players with their name and the clan of their stronghold), with a link to the Mercure hub (`Link: <…>; rel="mercure"`, `Mercure\Discovery`), built by `View/GameViewFactory::create(Game, Player $viewer)` into the readonly DTOs of `View/Model` (`GameView`, `PlayerView`, `StackView`, `CardView`) and serialized in snake case. A read goes neither through the bus nor through `GameLockMiddleware`. Same errors as the messages API (401, 403, 404). The `ETag` is the version of the game (also `version` in the view): the view only depends on the state and the viewer, so a player sending the ETag they have (`If-None-Match`) gets a 304 until the game changes; the response is `private, no-cache`. The visibility rules only depend on the state, never on the game place, and those of the cards are written once, in `View/Visibility` (shared with the log): decks and the opponents' hands are sent as counts (`cards: null`), a face-down card has no `code` (except a province for its owner) but its `side` (conflict, dynasty, province…: its back); the secret information of `PlayerState` (`pendingHonorBid`, `strongholdProvinceId`) goes to its owner only (in the factory); everything else is public. Cards are sent by code: the client reads them from `GET /api/cards`. New secret information must be stored apart from what is public, and masked in the factory. `available_actions` lists the types of the public messages the viewer can send now (`AvailableActionsResolver`, none once the game has ended): an action is listed when its handler's `assertAvailable()` passes, its payload can still be rejected.
- `GET /api/cards` and `GET /api/cards/{code}` (`ApiCardsController`): the cards as printed (`LogicalCard`), every card sorted by code or one card, built by `View/LogicalCardViewFactory` into `View/Model/LogicalCardView` (code, printed attributes, `ability_timings`, `ability_granted_to_attached`, `image_url` of its first printing with an image (`Printing::imageUrl`, from the fixtures; the engine does not use it); not the packs), serialized in snake case. Public (no token) and cacheable, like `GET /api/actions`; 404 `card_not_found` for an unknown code.
- `POST /api/guests` (`ApiGuestsController`): anyone gets a guest account, a human user with the name they chose (`{"name": ...}`, 1 to 64 characters) and no identity, with a session token: 201 `{"user_id", "name", "token"}` (`View/Model/GuestView`), the only time the token is sent. Public.
- `POST /api/accounts` (`ApiAccountsController`): a human creates the account they sign in to, `{"username", "password", "clan"}` (the preferred clan, a Great Clan: the account gets a copy of its starter deck). A guest sends their token and keeps their user and their name (no `name` in the body); anyone else also sends their name at court (`"name"`, 1 to 64 characters) and gets a new user. 201 `{"user_id", "name", "username", "preferred_clan", "settings", "token"}` (`View/Model/AccountView`, also sent by `POST /api/sessions`) with a new session token. Errors: 400 `invalid_payload` (structure: fields missing, not strings or unexpected), 422 `validation_failed` (values, checked by the Validator on `Model/AccountRequest`, and a username taken whatever its case: "This username is taken."), 409 `already_registered` (a token of a user who has an account, or of a bot), 401 an unknown token. Public.
- `POST /api/sessions` and `DELETE /api/sessions/current` (`ApiSessionsController`): signing in, `{"username", "password"}` (the username whatever its case): 201 with a new session token, like an account created; 401 `invalid_credentials`, the same for an unknown username and a wrong password (an unknown username hashes the password too, so that the time does not tell). Each attempt counts against two limits (`config/packages/rate_limiter.yaml`, sliding windows: 5 a minute by username, 20 a minute by IP), a success resets the count of the username: 429 `too_many_attempts` with `Retry-After`. Signing out revokes the session token of the request (204); an API key is not revoked this way (409 `not_a_session_token`). Signing in is public.
- `POST /api/bot-games` (`ApiBotGamesController`): a game against the house bot, without the queue: the user plays a deck they can use (`{"deck_id": ...}`), the bot another starter deck drawn at random; `Service/GameLauncher/BotGameLauncher` dispatches `CreateGame` then `JoinGame` for the user and the bot. 201 `{"game_id", "player_id", "opponent": {"user_id", "name", "deck_id"}}` (`View/Model/BotGameView`); 422 `deck_not_found`, 503 `bot_unavailable` when the house bot (`HOUSE_BOT_ID`) is not a bot user.
- `GET /api/self` (`ApiSelfController`): the authenticated user, `{"user_id", "name", "username", "preferred_clan", "settings"}` (`View/Model/SelfView`, `username` and `preferred_clan` null for a guest or a bot; `settings`: `{"card_display": "drawn" | "images", "theme": "auto" | "light" | "dark"}`). `PATCH /api/self` `{"name", "preferred_clan", "settings"}` (any of them; a setting left out is kept): changes their name at court (1 to 64 characters), their preferred clan or their settings (400 `invalid_payload`, 422 `validation_failed`), 200 with the user. `GET /api/self/subscription`: their subscription to the Mercure hub (`View/Model/SubscriptionView`: the public URL of the hub, a subscriber token for an hour, their topic; `no-store`), see "Other services". `GET /api/self/games`: their games, in progress or ended, the last joined first (`View/Model/UserGameView`: id, their `player_id`, `version`, `ended`, the users in player order), so that a user matched by the queue finds their game (`GameRepository::findByUser()`, a single query).
- `GET /api/decks`, `GET /api/decks/{id}` and `POST /api/decks` (`ApiDecksController`): the decks the authenticated user can use (their own and the starter decks; the others are not found, 404 `deck_not_found`), and the import of a deck: `{"name": ..., "format": "emeralddb", "cards": {"<card id>": <quantity>}}`, 201 with the deck (`View/Model/DeckView`). `Service/Deck/DeckImporter` converts the ids of the format to codes (`Service/Deck/DeckFormatInterface`, one tagged service per format: `codes` for the codes of the engine, `emeralddb` through the external cards), then checks the deckbuilding rules of the Stronghold format (`Service/Deck/DeckConstructionValidator`, not the banned and restricted lists). Errors: 400 `invalid_payload` (structure, with `violations`), 422 `invalid_deck` (unknown format, card unknown to the format, broken rule; `violations` on `format`, `cards[<id>]` or `cards`).
- `GET`, `POST` and `DELETE /api/queue` (`ApiQueueController`): the matchmaking queue. A user joins it with a deck they can use (`{"deck_id": ...}`, 204; 409 `already_queued`, 422 `deck_not_found`) and is matched at once when another candidate waits; `GET` gives the deck they wait with (404 `not_queued` once matched or left).
- `GET /api/games/{id}/log?since={version}` (`ApiGamesController`): the log of the game after a version (0 by default) as the authenticated player reads it (`View/GameLogViewFactory`): the messages handled on the game (`version`, `type`, sender `player_id`, never the payload), each with its entries (`template`, `params`) masked for the reader. Same errors and `ETag` as the view, 400 `invalid_since`, 400 `invalid_wait`. It is also a long-poll: with `wait={seconds}` (0 to 30), the response waits until the version is greater than `since` (`Service/GameUpdateWaiter`, polling the version in the database through the Symfony clock), then sends what changed, or the log as is (no message, or a 304) once the time is up; a game that has ended answers at once.
- MCP server (`symfony/mcp-bundle`, `config/packages/mcp.yaml`): `/api/mcp` (HTTP transport), for the programs playing as a bot (`ROLE_BOT`, API key in `Authorization: Bearer`, under the firewall of the API). Its tools are services of `src/Mcp` with a `#[McpTool]` method: the doc comment of the method and its `@param` describe the tool, the types and `#[Schema]` give the schema of the arguments, which the server checks before the call; a tool returns an array (the structured content) and reports an error with a `ToolCallException`. The user is read through `Security`. The tools give a bot what the HTTP API gives a player, so that an agent needs nothing else: `list_decks`, `join_queue` / `leave_queue` (`Service/MatchMaking/MatchMakingQueue`, shared with `/api/queue`), `list_my_games` and `wait_for_game` (the long-poll on the games of the bot, until one is in progress: `Service/GameStartWaiter`), `get_game` (the view of `GameViewFactory`), `get_cards` (cards by code, up to 50), and `wait_for_update`, the long-poll on the log (`Service/GameUpdateWaiter`, `GameLogViewFactory`). A list is returned in an object (`{"games": [...]}`), the structured content of a tool being an object. Each public message is also a tool named after its type (`Mcp/MessageToolLoader`, an `mcp.loader` registering a `Mcp/MessageTool` per message): its arguments are the schema of the payload (`MessageSchemaFactory`) with `game_id` and an optional `expected_version`; it returns the new `version`, and a rejected message is a tool error whose text is the problem of the HTTP API. A new public message is a new tool, with nothing to write. The bundle builds PSR-7 messages with `nyholm/psr7`. `agent/` makes Claude Code play as a bot through this server (`agent/play.sh <API key> [deck]`): `PLAYER.md`, the prompt of the player, and `mcp.json`; it runs in a temporary directory with the rules (`doc/`) and nothing else of the repository.
- Development console: `/console` (`ConsoleController`) is a command line in the browser (`assets/console`, ES modules served by AssetMapper, no build) that calls the HTTP API with a token kept by the tab and follows the notifications of the hub; beside it, the actions the user can send now (clicking one starts the command) and the image of the card under the pointer. It interprets the commands typed (`/help`), never runs them as code: one command per public message, built from `GET /api/actions` (positional or `key=value` arguments, cards by the shortest unique prefix of their id or by name, players by `me` / `opp`), views of the game (`/state`, `/hand`, `/provinces`, `/board`…) and of the account (`/decks`, `/upload-deck`, `/queue`, `/games`). On `game_updated`, it reads the view and the log again; on `game_started` (the queue has matched the user), it plays the new game.
- Console commands (`src/Command`) drive the rest of the engine; `app:game:log <id> [--as=<user>]` shows the log as a player (or a spectator) reads it.

### Web client (`front/`)

The site of the players, a single-page application (Vue 3, vue-router, Vite, TypeScript) that only talks to the HTTP API, on the same origin. In development, the `node` service runs the Vite server and nginx sends it every path but `/api`, `/console`, `/assets`, `/bundles` and the profiler, which go to Symfony; in production, `npm run build` gives static files (`front/dist`) for nginx, every unknown path falling back to `index.html`. Desktop only: designed for 1536px, at least 1280px wide (`min-width` of the body).

- **Newcomers**: the way to a first game, for a player who knows the game but not the site: the clan (`/`, the seven Great Clans with their starter deck, stronghold and champion read from `GET /api/cards/{code}`), the name at court (`/name`, drawn from the families of the clan, `lib/names.ts`), the opponent (`/opponent`: `POST /api/guests`, then `POST /api/bot-games`), then the game (`/games/:id`). The choices are kept by the tab (`lib/newcomer.ts`, `sessionStorage`), the guest account by the browser (`lib/session.ts`, `localStorage`: the same name keeps the same guest; an invalid token makes a new one). An account plays the introductory game under its own name.
- **Accounts** (`lib/session.ts`, `lib/credentials.ts`: the rules of the username and the password, checked before sending): sign in (`/login`, from the header: `POST /api/sessions`), create an account (`/signup`: the preferred clan first (`components/ClanPicker.vue`), prefilled for a guest with the clan of their last game, else of their way as a newcomer, else drawn at random (`suggestedClan()`), then a username and a password; a guest keeps their user, their name at court and their games; anyone else gets a name at court drawn by the client from the families of the clan; offered to a guest at the end of a game), the account (`/account`: the username, the preferred clan, the name at court and how the board draws the cards (drawn or their images) and the appearance (day, night or as the system) changed with `PATCH /api/self`, the linked accounts to come, sign out with `DELETE /api/sessions/current`), the queue (`/queue`, empty for now). The session (`session`, a ref) knows whether it is a guest (no username); the header shows the name of an account, else the way to sign in.
- **Game in progress** (`components/GameInProgressBanner.vue`, under the header): the last game the user joined that has not ended (`lib/gameInProgress.ts`: `GET /api/self/games`, then the view of the game for the name of the opponent), to rejoin it; read again on every page and when the session changes (a guest coming back, an account signed in to), not shown on the dark screen of the queue.
- **Game** (`views/GameView.vue`, full window: no header nor footer, `meta.fullscreen`): the board on the left, a bar of 340px on the right. `lib/useGame.ts` reads the view (`GET /api/games/{id}`, with the token of the session) and the log (`?since=`), follows the topic of the game on the Mercure hub (`lib/hub.ts`: the subscriber token of `GET /api/self/subscription` in the `authorization` query parameter, a new one once the hub refuses the connection, from the last update received), reads both again on each notification, reads the cards shown (`GET /api/cards/{code}`, their images loaded beforehand) and sends the messages with the version seen (`If-Match`: a 412 reads the game again). Pure logic, tested, in `lib/`: `board.ts` reads the view (provinces with what lies on them, characters with their attachments, the step of each place with its title, help and hint, the rings, the conflicts left) and prefills the totals the players declare (skills with attachments and personal honor, or the skill recorded; strength of a province with the bonus of the stronghold; glory count; fate of the stronghold; dueling statistic), which the player confirms or corrects; `cardActions.ts` lists what a card offers from where it is and the available actions; `logText.ts` writes the entries of the log from the point of view of the viewer ("You pass", "Opp. passes"), the cards apart so that their names show their image; `preview.ts` places the image of the hovered card; `tooltip.ts` the texts shown on hover (`v-tip`, drawn by `TooltipLayer.vue`), e.g. the effect of a ring.
  - **Board** (`components/game/GameBoard.vue`): laid out for the step. The whole board by default (the opponent's provinces small at the top, the characters at home, the viewer's provinces, the hand, dimmed when it cannot be played); the choice of the stronghold province during setup; the declaration of a conflict (the opponent's provinces to attack, the rings, the type, the attackers to choose; the viewer's provinces and hand fold into a line); a conflict (`ConflictField.vue`: the contested ring and province, the opponent's side above the viewer's, the skill of each side, declared or computed; the characters at home fold into a line, the defenders are chosen there; once the result is determined, the winner, the broken province and the effect of the ring). A click on a folded line unfolds it until the next step. While revealing the dynasty cards, a click on a face-down card of the viewer turns it face up. Once the game has ended, the board darkens under the result. A card (`GameCard.vue`) shows its face or its back (the ensō), or, when the account prefers the images (`session.cardDisplay`), the image of the card or the back of its side (`assets/images`), its skills marked only when they differ from the printed ones; bowed sideways, its fate and personal honor, the current skills of a character (recorded by a player, or computed from the cards: shown differently); hovered, its image appears beside it after 150ms (`CardPreview.vue`: above and to the right of the viewer's cards, below and to the right of the opponent's, on the left when there is no room).
  - **Card opened** (`CardDialog.vue`, a click on a card): its image in the middle of the darkened screen, and beside it what can be done with it, the same for the cards of both players: activate its abilities (and those its attachments grant it; interrupts and reactions are only triggered from here), play it (cost and fate prefilled, the target of an attachment), bow or ready, honor or dishonor, place or remove fate, move it to or from the conflict, record its skills, challenge to a duel, return it to hand, sacrifice or discard it. The effects on a player (honor, draw, shuffle…) are in `PlayerDialog.vue`, from the bar.
  - **Bar** (`GameSidebar.vue`): the phases, the step and what to do in it (`ActionPanel.vue`: pass, end the resolution, collect fate, bid, declare the conflict or the defenders with what is chosen on the board, declare the totals, claim the Imperial Favor, the duel), the players ("You" and "Opponent" on the tint of their clan, `PlayerChip.vue`: names can be long and both players can be of the same clan; honor, fate, hand, deck, conflicts left), the rings (unclaimed with their fate, contested, claimed by whom) and the Imperial Favor, the last lines of the log (all of it in `LogDrawer.vue`).

### Workflows

Six `state_machine` workflows defined in PHP in `config/packages/workflows.php` (Symfony 7.4 array-shape config, `App::config()`; keys are checked by PHPStan against `config/reference.php`): `game` plus one per card type (e.g. dynasty card: `draw_card`, `turn_faceup`, `turn_facedown`, `play`, `discard`). Use the place constants of the card classes and enums in metadata (`StackType::Hand`, `Orientation::FaceUp`), and the helpers of `Workflow/WorkflowConfig` (`transition()`, `cardWorkflow()`, `bowAndReady()`, `triggerAbility()`). Only the `game` places carrying metadata are declared (`places`); the others come from the transitions. Audit trail is on (`workflow` log channel).

**Card place = stack type + orientation.** A card's workflow place is not stored: `PhysicalCard::getCurrentPlace()` computes it with the `getPlace(StackType, Orientation)` mapping of each card class (e.g. a province `UpsideDown` is broken, a dynasty card `FaceUp` in a province is `on_province_faceup`). A place stands for a set of available transitions, so orientations that do not change them share a place: a bowed card (`Sideways`) is still `in_play`, and `bow` / `ready` are transitions from `in_play` to itself. Only what is not a physical position (honor status, fate tokens…) goes in the card `state`. Card workflows use `Workflow/CardMarkingStore`, which reads that computed place and, after a transition, checks that the card really ended up in the target place.

Card transitions declare their effect in metadata, applied by the generic `Workflow/CardTransitionListener`: `stack` (StackType the card moves to) and `orientation` (Orientation it takes; required on a move, otherwise the card keeps its orientation). Target stack: a character entering play gets a new stack (`PhysicalCard::entersPlayInNewStack()`); otherwise the context `stack` (e.g. the character or province an attachment goes on, possibly an opponent's), else the player's unique stack. `CardMarkingStore` rejects a target stack the card cannot be in. Write a specific listener only for what metadata cannot express, like `Workflow/LeavePlayListener` (consequences of any transition out of `in_play`: personal honor, tokens, attachments, conflict participation). Never move or turn a card outside a transition.

The `game` workflow models the round sequence; a new place exists when the phase **and** the available player actions differ. Place metadata:

- `action_window`: players can trigger action abilities (`TriggerActionAbility`) and play cards from hand (`PlayCharacterFromHand`, `PlayAttachment`, `PlayActionEvent`); `play_from_hand: false` forbids characters and attachments from hand (1.4). `OpportunityService::assertCanTakeAction()` checks it. The `trigger_ability` transition of a card workflow (from a place to itself) lists where the abilities of a card can be used (`TriggerActionAbility`, `TriggerInterruptAbility`, `TriggerReactionAbility`).
- `opportunities`: players have opportunities to act, in player order or simultaneously, and can pass them (`PassOpportunity`); the step ends once every player has passed (`AllPlayersPassedGuardListener`). Its value is an `Enum/PassingRule`: `Final` (passing forfeits the remaining opportunities of the step) or `Consecutive` (action windows: a player who acts cancels the passes, and the window closes once every player has passed consecutively).

Transition metadata: `auto` and `priority` (see `WorkflowTransitionMiddleware`), and `log`, the template of the entry the transition writes in the log of the game (required on every transition of every workflow, see "Game log"). `end_game` leads from every place of a started game (`WorkflowConfig::placesOf()`) to the final place `game_ended` (`Game::STATE_ENDED`); it is automatic with the highest priority, so the game ends as soon as a player meets a victory condition, before any other automatic transition.

Behaviour lives in listeners under `src/Workflow/<WorkflowName>/`, named after the transition/place and the event type: `...GuardListener` (blocks a transition until conditions are met), `...TransitionListener`, `...EnterListener`.

### Game flow

- **Values from players**: since the engine does not apply card effects, a step whose outcome cards can modify (e.g. the amount of fate collected) is a player action carrying the value; an `auto` transition guarded on every player having acted then moves the game on.
- **Turn records**: what a player did during the round goes in the turn records of `PlayerState`, reset at the end of the round (`fate_phase_ended`).
- **Player order**: stored in `GameState` (`playerIds`, fixed by `start_game` from the order of arrival, `Player::joinRank`; the first player changes, not the order).
- **Opportunities to act**: the players who have the opportunity to act are the active players of `GameState` (`activePlayerIds`); the handler of each action rejects a player who is not active (`NotActivePlayerException`). The enter listener of the step activates them (`FirstPlayerOpportunityEnterListener` and `AllPlayersOpportunityEnterListener` cover the common cases):
  - in steps resolved in player order, only the first player: the handler gives the opportunity to act to the next player (`GameState::getNextPlayerId()` / `getPlayerIdsAfter()`, resolved with `Game::getPlayer()`). An action that requires follow-up actions keeps the opportunity with the player, who ends it with `EndResolution` (see below);
  - in steps where players act simultaneously (e.g. `reveal_honor_dials`, the `react_to_*` reaction windows of a conflict), every player: they keep their opportunity until they pass.

  A player who passes (`PassOpportunity`, in a place marked `opportunities`; `PlayerState::passed`, reset by the enter listener of the step) is no longer active and is skipped by `Service/OpportunityService`. In an action window (`PassingRule::Consecutive`), a player who ends their action (`EndResolution`) resets every pass, so the players who had passed get opportunities to act again.
- **Resolving what a player plays**: an active player who has done nothing passes (`PassOpportunity`); once they act (`PlayActionEvent`, `TriggerActionAbility`, `PlayCharacterFromHand`, `PlayAttachment`, `PlayCharacterFromProvince`: `OpportunityService::takeAction()`, `PlayerState::acted`), they apply its effects with other messages, then end it (`EndResolution`), which ends their opportunity: they cannot pass meanwhile (`ResolutionInProgressException`), and `EndResolution` is rejected when there is nothing to end (`NothingToResolveException`). An interrupt or a reaction (`PlayInterruptEvent`, `PlayReactionEvent`, `TriggerInterruptAbility`, `TriggerReactionAbility`) is resolved the same way by any player, without using an opportunity to act: `PlayerState::resolvingInterruptsAndReactions` counts those not ended yet, and `EndResolution` ends the last one first, during a duel too; the action itself ends once no duel is being resolved. `available_actions` therefore never lists both `pass_opportunity` and `end_resolution`, and the view of each player shows `acted` and `resolving_interrupts_and_reactions`. Phase actions that move the game on (declaring a conflict, defenders, a bid…) and `InitiateDuel` (an effect of an ability) are not actions to end.
- **End of the game**: `Service/VictoryService` checks the victory conditions from the state (a player with 25 or more honor wins; a player who has conceded (`ConcedeGame`, `PlayerState::conceded`) or has no honor is eliminated and the last one standing wins; ties go to the first player, then in player order). The guard of `end_game` uses it, and its transition listener records `winnerId` and `victoryCondition` in `GameState`. Honor cannot go below 0 (`PlayerState::setHonor()`).
- **Duels**: a duel is not a place of the `game` workflow, since it returns to the action window it was initiated in: it is the `DuelState` of `GameState`, whose steps the messages move on (`InitiateDuel`, `BidHonor`, `DeclareDuelStatistic`, `EndDuel`). While a duel is being resolved, no action window is open and the players cannot pass or end their action (`OpportunityService::assertNoDuel()`); interrupts and reactions can be ended.
- **Interrupts and reactions** are initiated when their triggering condition occurs, not during an opportunity to act: `PlayInterruptEvent`, `PlayReactionEvent`, `TriggerInterruptAbility` and `TriggerReactionAbility` are accepted from any player in any place, during a duel too, and change no opportunity: the player ends them with `EndResolution`. Action events and abilities (`PlayActionEvent`, `TriggerActionAbility`) require the opportunity to act in an action window. An event is played with the message of its timing (`AbilityTiming`), and its message is available only with such an event in hand; the abilities of cards are not checked against their timings, since cards gain and lose abilities.
- **Secret information**: what a player knows and their opponents do not is stored apart from what is public, so that its visibility only depends on the state (e.g. `PlayerState::pendingHonorBid`, the secret bid, and `honorBid`, the revealed one).
- **Refilling the provinces**: once a dynasty card has left a province (played from it, discarded) and no dynasty card remains on it (a holding keeps it from being refilled), the engine refills it at once, face down, from the dynasty deck of its owner (`Service/ProvinceRefiller`, called by the handlers and listeners that move dynasty cards out of provinces). `FillProvince` remains for setup and the effects that fill a province.
- **Costs and effects**: board manipulations (`BowCard`, `LoseHonor`, `DiscardCard`, `HonorCharacter`, `MoveToConflict`…) are accepted in any place, from any player of the game, on any card or player, since the engine does not know which ability is being resolved.
- **Totals from players**: the engine does not compute skills, province strengths or glory, which card effects modify: players declare them (`DeclareConflictSkill`, `DeclareProvinceStrength`, `DeclareGloryCount`) and the engine applies the rules to the declared values (winner, broken provinces, Imperial Favor). The current skill of a character can also be recorded for every player to see (`SetCharacterSkill` / `ResetCharacterSkill`, every modifier applied, cleared when it leaves play); it is not used by the engine.

### Game log

Every change of the state of a game writes an entry in its log (`GameLogEntry`): a template in English whose placeholders (`{player} loses {amount} honor`) are replaced by its params, so that the log can be read as is and translated by the client. The entry belongs to the version of the game the message being handled leads to, automatic transitions included; a message writes any number of entries, ordered by id. The log is written by `GameLog/GameLogger`, from three sources:

- **Card transitions**: `GameLog/CardTransitionLogListener` writes the `log` metadata of the transition, when the card leaves its place (before the consequences of the transition), with the params `card`, `owner`, `from` and `to` (stacks).
- **Game transitions**: `GameLog/GameTransitionLogListener` writes the `log` metadata of the transition (no params), before its listeners.
- **Domain events**: a domain event of `src/Event` carrying the `#[GameLog('template')]` attribute (and implementing `Event/GameEventInterface`) writes its entry when it is dispatched, before its other listeners (`GameLog/GameLogEventListener`, registered by `App\Kernel` for every such event); the placeholders name its properties. Every change of the state that is not a transition dispatches one. Bookkeeping that follows from a logged transition is not logged: active players and passes reset when a step begins, turn records, honor dials reset, conflict and duel cleanup.

The log tells *what* changed, not why (the engine does not know the card effects); the client gets the type and the sender of each message beside its entries.

**Visibility of the params** (`GameLog/LogParam`): a param is `player`, `card`, `stack`, `ring`, `value` or `list`. A card or a value may be known to some players only: its visibility is null when public, else the list of the ids of the players who know it (empty: nobody). It is computed when the entry is written, from the state: a card is known to the players who see it before or after the transition (`View/Visibility`: its id when they see its stack, its code when they see its face), a property of an event marked `#[VisibleTo('player')]` only to that player (`#[VisibleTo]`: nobody), a card marked `#[Revealed]` to every player. `View/GameLogViewFactory` masks the log for each reader: a hidden card has no id nor code (no code when only its id is known), a hidden value has `hidden: true`; a reader who is not a player (spectators, to come) only sees what is public.

### Other services

- House bot (`Service/Bot`): the bot of the platform (user `HOUSE_BOT_ID`, `kyuden-bot` in the fixtures, owned by the user `kyuden`) plays the games of `POST /api/bot-games`. `HouseBotMiddleware` (first of the bus) schedules the game of every handled message; on `kernel.terminate`, once the response is sent, `HouseBot` plays in the scheduled games where it is a player, through the bus like any player, until it has nothing to do (at most 100 actions per request): before each message it clears the entity manager, so that `GameLockMiddleware` loads the game again, and sends the version it decided on (`ExpectedVersionStamp`): a stale version makes it decide again. The player sees its moves through the notifications of the game. `BotStrategy` chooses the action from the available ones: the framework steps only (stronghold province, revealing its facedown dynasty cards, fate of its stronghold, honor bid of 2, no defenders, the printed totals of its ready characters for skill and glory, the Imperial Favor on its military side), and it passes every opportunity: it plays no card and declares no conflict. `app:bot:play <game>` makes it play in a game.
- Matchmaking: `Service/MatchMaking/FifoMatchMakingService` pairs the candidates in their order of arrival, holding the lock of the queue (`CandidateRepository::withQueueLock()`, a PostgreSQL advisory lock); `Service/GameLauncher/AutomaticGameLauncher` creates the game through the bus (`CreateGame`, then `JoinGame` for each candidate: recorded as events, the game starts once both have joined) and removes the candidates. It runs when a user joins the queue (`MatchMakingQueue`, for the HTTP API and the MCP tools), or with `app:matchmaking`.
- Notifications: `NotificationInterface` objects sent through `NotifierInterface`; `MercureNotifier` publishes them as private updates of the hub, `LoggerNotifier` logs them.
- Security: stateless access-token authentication: `Security/AccessTokenHandler` finds the `AccessToken` by the hash of the token, with its `User` (a single query; an unknown token gets a 401). A user is matched to the player of a game through `Player::user`. `Security/AccessTokenIssuer` issues the tokens (random, prefixed `l5r_`, returned once). The password of a human only gets a session token (`POST /api/sessions`); the API also issues one to a guest (`POST /api/guests`) and to an account created (`POST /api/accounts`). The bots and their API keys are created by console commands (`app:user:create`, with `--username` for a human who signs in: the password is asked; `app:token:create`, `app:token:revoke`), and the fixtures hold users with known tokens and passwords (`DataFixtures/UserFixtures`, in clear, development and tests only: john and jane have an account, with a preferred clan and their copy of its starter deck, harry and sally are guests).
- Mercure: every topic is private (`Notification/Topics`): `/games/{id}` (`game_updated`: its id and version, no data of the game) and `/users/{id}` (`game_started`). A subscriber sends a token (`Notifier/SubscriptionFactory`, `GET /api/self/subscription`) whose `subscribe` claim is the topic of the user and the template of the topics of their games (`/users/{id}/games/{gameId}`); an update of a game also carries that topic for each of its players, so that the token of a user reads every game they play, joined before or after it was issued, and no other. Browsers cannot set headers on an `EventSource`: the token goes in the `authorization` query parameter, and lasts an hour. In development, the server publishes to the `mercure` service of the Docker network (`MERCURE_URL`), the browsers subscribe to `MERCURE_PUBLIC_URL` (no anonymous subscriber).
- Exceptions: `Exception/Data` (missing/mismatched data) vs `Exception/Rules` (game-rule violations).
