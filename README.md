# Kyūden

[![Test](https://github.com/alsciende/kyuden/actions/workflows/test.yml/badge.svg?branch=main)](https://github.com/alsciende/kyuden/actions/workflows/test.yml)
[![codecov](https://codecov.io/github/alsciende/kyuden/graph/badge.svg)](https://codecov.io/github/alsciende/kyuden)

[kyuden.app](https://kyuden.app): server-side engine to play **Legend of the Five Rings LCG** (Fantasy Flight Games). PHP 8.5 (FrankenPHP), Symfony 7.4, Doctrine ORM on PostgreSQL, Symfony Messenger, Symfony Workflow, Mercure; and its web client (`front/`): Vue 3, Vite, TypeScript.

## Installation

You need git, make and Docker.

```shell
git clone <this repo>
cd kyuden
make build
make up
make install
make db
make front-install
open http://localhost:8080
```

## Production

`docker/production/Dockerfile` builds one image from the root of the repository: FrankenPHP (`docker/production/app/Caddyfile`) with the application (no development dependencies, opcache with preloading, cache warmed), the web client (`front/dist`, built in the image, showing in its footer, after the name of the site, the release it was built for: the build argument `KYUDEN_VERSION`, the git tag in `release.yml`, `local` for `make prod-build`, `dev` otherwise) and, among its links, the official Discord server (the build argument `DISCORD_URL`, the variable `DISCORD_URL` of the repository in `release.yml`, `DISCORD_URL` of the shell for `make prod-build` and for the Vite server of development; no link when empty) and the Mercure hub. The same image runs the worker (`bin/console messenger:consume async`, the service `worker`, see "Other services"). It terminates TLS for the domain of `SERVER_NAME` (`kyuden.app`: a certificate from Let's Encrypt, renewed by Caddy and kept with the history of Mercure in the volume `caddy_data`; HTTP redirected to HTTPS; HSTS), or listens on HTTP only (`:80`). The hub is a site of its own on port 8000 of the container (a configuration has a single hub, and each port is another server), which the host does not publish: Symfony publishes to it there (`MERCURE_URL`: `127.0.0.1:8000` for the application, `app:8000` for the worker), the site proxies the browsers to it on its origin (`/.well-known/mercure`, `MERCURE_PUBLIC_URL`). `compose.yaml` adds PostgreSQL and the worker. On every start of the application, the entrypoint of the image brings the database up to date before FrankenPHP serves anything: the Doctrine migrations (`migrations/`), the card database (`app:cards:import`) and the house bot (`app:house-bot:create`); a failed step stops the container. The worker runs none of these steps (the entrypoint runs them for FrankenPHP only) and starts once the application is healthy.

Continuous integration (GitHub Actions): every commit pushed, on any branch, runs `.github/workflows/test.yml`, the linters and the tests on the development stack (`CI` set: `make` runs `docker compose exec` without a terminal); a new commit on the branch cancels the run of the previous one. The tests of PHP run with the code coverage (`make coverage`): the HTML report is an artifact of the run (`coverage-report`), and the Clover report goes to Codecov (secret `CODECOV_TOKEN`, paths of the container mapped by `codecov.yml`). It caches the dependencies (PHP, npm, by their lock files) and the development image `symfony`. Releases: every git tag, on any branch, runs `.github/workflows/release.yml`: the same tests (`test.yml`), then the build of the image (`linux/amd64`), pushed to the GitHub Container Registry as `ghcr.io/alsciende/kyuden-app:<tag>` (public, no `latest`). The production host only needs `docker/production` (`compose.yaml`, `deploy.sh` and the two files below), not the code: it deploys the release named by `KYUDEN_VERSION` in `.env`. A tag `vX.Y.Z` of a commit of `main` is then deployed (job `deploy`, GitHub environment `production`, one deployment at a time): the workflow connects to the host over SSH as `deploy` with a key whose forced command is `deploy.sh`, sending the tag; the script checks it, writes it in `.env`, pulls the image of the application, stops the worker (so that its code does not run on the database the new release migrates), recreates the container of the application (not the database), waits for it to be healthy, then recreates the worker, restores `.env` if that fails, and prunes the unused images; the workflow then waits for `/api/actions` of the site (`DEPLOY_URL`) to answer.

```shell
cp docker/production/.env.dist docker/production/.env                # what the services share, and the release (KYUDEN_VERSION)
cp docker/production/symfony.env.dist docker/production/symfony.env  # the rest of the environment of the application
# replace every value of both files: those of the .dist files run the stack on a workstation, their secrets are public;
# SERVER_NAME=kyuden.app (its DNS pointing to the host, ports 80 and 443 open), HTTP_PORT=80, HTTPS_PORT=443;
# in symfony.env, SYMFONY_TRUSTED_HOSTS='^kyuden\.app$'
docker compose -f docker/production/compose.yaml --env-file docker/production/.env pull
docker compose -f docker/production/compose.yaml --env-file docker/production/.env up --detach
```

The continuous deployment needs, once, on the host (in `/opt/kyuden`, the files of `docker/production` and the two `.env`):

```shell
sudo useradd --create-home --shell /bin/sh --groups docker deploy  # no password: the key below only
sudo chown root:root /opt/kyuden /opt/kyuden/deploy.sh && sudo chmod 755 /opt/kyuden /opt/kyuden/deploy.sh
sudo chown root:deploy /opt/kyuden/.env && sudo chmod 660 /opt/kyuden/.env  # the only file deploy writes
sudo chown root:82 /opt/kyuden/symfony.env && sudo chmod 640 /opt/kyuden/symfony.env  # read by www-data (82) in the app container
ssh-keygen -t ed25519 -N '' -C github-actions-deploy -f deploy_key       # on a workstation, for this use only
# in ~deploy/.ssh/authorized_keys (700, 600, owned by deploy): the public key, restricted to the script
#   command="/opt/kyuden/deploy.sh",restrict ssh-ed25519 AAAA… github-actions-deploy
ssh-keyscan -t ed25519 <DEPLOY_HOST>   # compared with ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub on the host
```

In GitHub, the environment `production` (deployment tags `v*`) holds the secrets `DEPLOY_SSH_KEY` (the private key, then deleted from the workstation) and `DEPLOY_KNOWN_HOSTS` (the line of `ssh-keyscan`), and the variables `DEPLOY_HOST` (the name or IP the key is scanned for: `known_hosts` is indexed by it) and `DEPLOY_URL` (the URL of the site, without a trailing slash, e.g. `https://kyuden.app`). Being in the group `docker` amounts to root: the forced command is what keeps the key from doing anything but deploying a release.

`compose.yaml` and `deploy.sh` are copied again to the host when they change, with an account of the administrator (not `deploy`, whose key only runs `deploy.sh`): uploaded to their home, then installed by `install.sh` (`docker/production/install.sh`, copied once to the home of the administrator on the host, beside the directory `kyuden-upload`; `sudo install`: owned by `root`, `deploy.sh` in `755`, `compose.yaml` in `644`; it shows the differences, skips a file unchanged and lists `/opt/kyuden`):

```shell
scp docker/production/compose.yaml docker/production/deploy.sh <admin>@<DEPLOY_HOST>:kyuden-upload/
ssh -t <admin>@<DEPLOY_HOST> ./install.sh
```

Once, before: `ssh <admin>@<DEPLOY_HOST> mkdir -m 700 kyuden-upload`, then `scp docker/production/install.sh <admin>@<DEPLOY_HOST>:` (again when it changes).

`.env`, read by compose, holds what the services share (the database, the secret of Mercure): compose gives the application its `DATABASE_URL`, `MERCURE_URL`, `MERCURE_JWT_SECRET` (also the key of the tokens of the hub) and `SERVER_NAME`. The rest of the environment of the application is `symfony.env`, on the host, mounted read-only as its `.env` in the `app` container (it replaces the `.env` of the repository; the variables set by compose and the image, `APP_ENV` and `APP_DEBUG`, win over it), so that compose does not list every variable of Symfony. Both files stay out of git.

To try the production stack on a workstation, stop the development stack first (`make down`: both listen on port 8080 if `HTTP_PORT` says so, and the targets below use a compose project of their own, `kyuden-prod`, so that `make down` does not remove its containers). The image is built from the working tree under the tag `local` (the image of a release is `linux/amd64` only), which the targets set as `KYUDEN_VERSION`:

```shell
make down
cp docker/production/.env.dist docker/production/.env                # as is: the values of the .dist files run locally
cp docker/production/symfony.env.dist docker/production/symfony.env
make prod-build   # the image, ghcr.io/alsciende/kyuden-app:local
make prod-up      # migrations, card database and house bot, then http://localhost:8080 (SERVER_NAME=localhost make prod-up: HTTPS on HTTPS_PORT, certificate of the local authority of Caddy)
make prod-logs
make prod-down    # with its volumes: the next start begins with an empty database
make up
```

The database of production holds no user of the fixtures: play as a guest or create an account.

## MVP scope

- The engine acts as a **board**: it enforces the game flow (rounds, phases, framework steps) but **does not enforce card rules**.
- Only the **Stronghold format** (two players) is in scope.

The state of the implementation and the open points are listed in `HANDOFF.md`.

## Architecture

### Domain model (`src/Entity`)

- `LogicalCard`: the card as printed (title, cost, text), grouped in `Pack` via `Printing`. A `Pack` belongs to a `Cycle` (the core set, the clan packs, a cycle of chapter packs…), at its `position` in it; the cycles are ordered by their own `position`. What its text means for a game in progress is its script (see "Card scripts"): the timings of its triggered abilities among others.
- `PhysicalCard`: one copy of a card in a game, owned by a `Player`. Mapped superclass with one subclass per type in `src/Entity/CardTypes` (Conflict, Dynasty, Province, Role, Stronghold).
- `Stack`: ordered collection of physical cards (deck, hand, province, etc.; see `Enum/StackType`). The top card has the highest `position`. The stacks of the cards set aside out of play (`StackType::isSetAside()`) are created when a card first goes there (`Service/SetAsideStacks`): the cards a player has removed from the game (`RemovedFromGame`, one per player), and the cards under a card (`Underneath`, one per card, of the owner of that card, which it names: `Stack::host`, removed with it). When order matters, use `getOrderedCards()` / `getTopCards()`: the order of `getCards()` is not kept in sync with positions (e.g. after `moveCard()`).
- Shuffling (`Service/StackShuffler`, never `Randomizer::shuffleArray()` on cards directly) makes the players lose track of the cards: it deletes them and creates them again in random order with new ids (same logical card, player, stack and orientation, fresh state), so that an id seen before cannot be followed into a shuffled deck. Redistributing the cards of the provinces (`RedistributeProvinceCards`) gives new ids the same way. Code holding a card of a stack across a shuffle must read it again from the stack.
- `Enum/Orientation`: physical orientation of a card (`FaceDown`, `FaceUp`, `Sideways`, `UpsideDown`), stored on `PhysicalCard`. A new card takes the initial orientation of its class (`getInitialOrientation()`: face down, except stronghold and role); afterwards only workflow transitions change it.
- `Game`: friendly or not (`friendly`: a game of an invitation, not ranked; set by `CreateGame`); carries a `version`, the number of messages handled on it (incremented with each `Event`, so that the events of a game are numbered from 1, and when it last changed, `updatedAt`), and its own random generator (`getRandomizer()`, seeded by `CreateGame::seed`, engine state saved with the game) for every random draw (shuffles, first player, random discards, ids of the cards and stacks it creates: `generateId()`, salted by the id of the game, so that a game replayed under another id draws the same values without creating the same ids), so that replaying the event log gives the same game. Never draw outside of it. A game may be the replay of another one (`replayOf`, for the user who follows it, `replayUser`): a copy rebuilt from the events of a game that has ended (see "Replay").
- `Deck`: quantity by card code; each copy becomes a physical card when a game starts (`Deck::getCardCodes()`). A deck belongs to the user who imported it; a deck without owner (the starter decks, `fixtures/starter_decks/<deck id>.json`) can be used by every user. An account gets its own copy of the starter deck of its preferred clan when it is created (`Service/Deck/StarterDeckCopier`). Its `contentHash` (SHA-256 of a line `code:quantity` per card, sorted by code: `Deck::hashCards()`, kept in sync by `setCards()`) identifies its cards whatever its name: a user does not import the same cards twice (see the API). Its owner deletes it (`Service/Deck/DeckDeleter`): a deck never played is removed, a deck played in a game stays for its players, marked deleted (`deletedAt`): nobody can use it any more (`isUsableBy()`), and importing its cards again restores it.
- `ExternalCard`: links the id of a card in an external database (`Enum/CardSource`, e.g. EmeraldDB) to a `LogicalCard`, to import the decks built there; loaded from `fixtures/external_cards/<source>.json` (card code by external id).
- `Event`: persisted record of every handled action, numbered by the version of its game. It holds the payload of the message, secret information included (the seed of `CreateGame`, secret bids…): it is never shown to the players, who read the log of the game (see below).
- `GameLogEntry`: a line of the log of a game, what changed in it (see "Game log").
- `Candidate`: a player waiting in the matchmaking queue, with the invitation they wait with, if any.
- `Spectator`: an account watching a game (its key: the game and the user), with when it arrived and when it last read the game; not part of the game (no event, no log), see "Other services".
- `Invitation`: an invitation of an account to a friendly game, for its bot (an API key limited to it) or for a friend (a code: `Security/InvitationCode`); open, used once (the game it led to), expiring after 24 hours. Its host and its guest are matched together only (see "Other services").
- `LinkedAccount`: an identity at a provider (OAuth2, `Enum/OAuthProvider`: Google, Discord) linked to an account, which then signs in with it: only the identifier of the identity at the provider (`subject`), no personal data; an identity is linked to one account at most, an account to one identity of each provider at most.
- `User`: an account, human or bot (`Enum/UserType`); a bot is owned by a human. Its id is its user identifier (a UUID, except the users of the fixtures). Its `name` is its name at court, what the other players see (not unique). A human signs in with a `username` (`[A-Za-z0-9_]{3,32}`, unique whatever its case: `usernameCanonical`) and a password (8 to 4096 characters, hashed by the `auto` hasher of Symfony); a human without a username is a guest (`isGuest()`), who becomes an account by registering (`register()`, `Security/AccountRegistrar`): the same user, so their games, decks and tokens stay theirs. An account has a preferred clan (`preferredClan`, one of the Great Clans: `Enum/Clan::greatClans()`), chosen when it is created and changed at any time; null for a guest or a bot. A user has settings (`settings`, JSON read through `Model/UserSettings`: a missing setting takes its default), for now how the web client draws the cards (`cardDisplay`, `Enum/CardDisplay`: `drawn` or `images`) and whether it is light or dark (`theme`, `Enum/Theme`: `auto`, `light` or `dark`). A `Player` and a `Candidate` belong to a user (`Player::getUserId()` reads the id without loading the user); a player also carries when they last read their game (`lastSeenAt`, see "Abandoned games"); a user is a candidate at most once. `AccessToken`: a token of a user, stored as its SHA-256 hash, either a session or an API key (`Enum/AccessTokenType`); only a bot gets API keys, so that a program playing through one is known as a bot (`ROLE_BOT`). The key of an invitation for a bot is limited to it: valid while it waits, then until the end of its game, and it joins the queue with it.

### State

`Game`, `Player` and `PhysicalCard` implement `State/Model/StatefulInterface`: they carry a JSON `state` field, decoded by the managers in `src/State/Manager` (`GameStateManager`, `PlayerStateManager`, `CardStateManager`) into `GameState` / `PlayerState` / `CardState` (fate on the card, honor tokens on a province or a holding, personal honor, the skills set by the players, the controller when another player has taken control of it). `GameState` also holds the rings (`RingState`: fate, claiming player and the type of the conflict it was claimed in), the Imperial Favor and the conflict being resolved (`ConflictState`: players, contested ring, type, attacked provinces, participating characters by card id) and the duel being resolved (`DuelState`: players, characters involved, step, declared statistics, result). Modify it through `withState(closure)`, which decodes, runs the callback and re-encodes.

### Action pipeline

1. A player action is a Messenger message in `src/Message`, implementing `ActionInterface` (or `PlayerActionInterface` when it has a player) and tagged with `#[AppAction]`, which makes it discoverable by `Service/ActionMessageRegistry`. The attribute says whether players can send it through the API (`public`, false for the platform actions: `CreateGame`, `JoinGame`, and those the engine sends itself: `SetHonor`, the starting honor), and whether it is special (`special`: an effect few cards have, such as `PutCardOnDeck`, `InitiateDuel` or `SwitchRing`, which the web client offers apart; the engine accepts it like any other) Its `playerId` is always the player sending it; the player an effect applies to is a separate field (`targetPlayerId`, or `giverId` / `recipientId` for `TransferHonor`). Messages hold ids (game, player, card) as strings, not entities. The message is the single source of truth of its payload: the values are checked by constraints of the Validator on the arguments of its constructor (`#[Assert\…]`), each field is described by a `#[Description]` attribute and the message by its class doc comment, from which `Service/Api/MessageSchemaFactory` builds the JSON schema of the payload.
2. Its handler in `src/MessageHandler` (`#[AsMessageHandler]`, `final readonly`) loads entities through repositories and changes the state, usually by applying a transition on the relevant workflow. The handler of a public player action implements `MessageHandler/PlayerActionHandlerInterface`: `assertAvailable(Game, Player)` checks what the action requires from the state whatever its payload (game place, active player, duel step…), throwing the same rules exceptions as the rest of the handling; it only reads the state. The handler calls it before handling the message, and `Service/AvailableActionsResolver` calls it to list the actions a player can send now, so that both cannot diverge. `App\Kernel` maps each of these handlers to its message (type of the parameter of `__invoke()`) in a service locator; a test checks that every public message has one.
3. Middlewares (order in `config/packages/messenger.yaml`):
   - `validation`: checks the constraints of the message (`ValidationFailedException`), before any lock or transaction. The handlers only check what needs the state.
   - `GameUpdatedNotificationMiddleware`: once the transaction is committed, notifies the players that the game has changed (`GameUpdatedNotification`: Mercure topic `/games/{id}`, with the new version and no data of the game), and, once the last player has joined (`JoinGame`, the game has started), every player that it has started (`GameStartedNotification`, `game_started` on `/users/{id}`, with the game and the player of each user). Nothing is notified when the handling fails.
   - Doctrine transaction: commits everything at the end.
   - `GameLockMiddleware`: locks the game row (`SELECT … FOR UPDATE`) before the handling, so the actions on a game and the automatic transitions they lead to are handled one at a time. A game already loaded is locked but not reloaded: load nothing of the game before dispatching.
   - `GameVersionMiddleware`: rejects a message sent with an `ExpectedVersionStamp` (`Middleware/Stamp`) once the game has changed (`StaleVersionException`), before its handling. The expected version is a stamp, not part of the message, so that replaying an event never fails on it.
   - `GameEndedMiddleware`: rejects any action on a game that has ended (`GameEndedException`), before its handling.
   - `GameReplayMiddleware`: rejects any action on a replay (`ReplayReadOnlyException`) but the events it replays (`ReplayStamp`), whoever sends it.
   - `EventRecordingMiddleware`: once the message and its automatic transitions are handled, increments the version of the game (and sets `updatedAt` from the clock) and saves the message as an `Event` with that version. It comes before `WorkflowTransitionMiddleware`, so that the log entries of the automatic transitions belong to the version of the message that led to them.
   - `WorkflowTransitionMiddleware`: after the handling, repeatedly applies the enabled game transition marked `metadata.auto: true` with the highest `metadata.priority` (0 by default); two enabled automatic transitions sharing the highest priority throw a `LogicException`.
   - `ProvinceRefillMiddleware`: right after the handling, before the automatic transitions, refills the provinces the handlers have scheduled (see "Refilling the provinces").
4. `Service/EventPlayer` deserializes a stored `Event` (or a message name and payload) and re-dispatches it, so a game can be replayed from its event log. Messages must therefore stay serializable.

A handler does what a message does in every place. What depends on the step goes in a listener of a domain event (`src/Event`, named in the past tense: `OpportunityPassedEvent`) dispatched by the handler: the listener (`src/EventListener`, named after the place and the event, e.g. `PlayCardsFromProvincesOpportunityPassedListener`) checks the game place. The event carries the entities and the values its listeners need, computed before the state changes when necessary (`firstToPass`). These events are also the hook for cards reacting to what happens, and the entries of the log of the game (see "Game log"): a change of the state that is not a transition dispatches a domain event. A message that must behave differently in some step is a different message.

HTTP API (access token: `Authorization: Bearer <token>`, see "Other services" for authentication):

- `POST /api/games/{id}/messages` (`ApiGameMessagesController`, through `Service/Api/PlayerMessageSender`, shared with the MCP tools: checks, dispatch and the problem of a rejected message, `ApiProblemException`): a player of the game sends any public action message, `{"type": "pass_opportunity", "payload": {...}}`. The type is the snake case short name of the message class; the payload holds its constructor arguments in snake case (serializer name converter). `Service/Api/ApiMessageFactory` builds the message: the game comes from the URL, the player (sender) is the authenticated player (the payload cannot hold `game_id` nor `player_id`); the target of an effect is in the payload (`target_player_id`…). The controller only reads ids before dispatching (see `GameLockMiddleware`). Versions: the `ETag` of the response is the version of the game once the message is handled (`"12"`); with `If-Match` (a single ETag of the game, or `*`), the message is rejected with a 412 (`stale_version`) if the game has changed since. Responses: 204 once handled; errors are problem details (`application/problem+json`, `type` from the exception): 400 invalid body, type, payload (`invalid_payload`: structure of the payload, with `violations`) or `If-Match` (`invalid_if_match`); 401 no token; 403 not a player of the game; 404 unknown game; 409 forbidden by the rules in the current state (`Exception/Rules`, `WorkflowException`, workflow transition not enabled); 412 stale version; 422 payload referring to nothing in the game or with invalid values (`validation_failed`: constraints of the message, with `violations`). A violation has a `property_path` (snake case) and a `message`.
- `GET /api/actions` (`ApiActionsController`): the catalogue of the public messages, the JSON schema of the payload of each type (`MessageSchemaFactory`). Public (no token) and cacheable. The schemas are also committed in `schemas/messages` (`bin/console app:message-schemas:dump`), the snapshot of the contract of the API: a test fails when they differ from the messages.
- `GET /api/games/{id}` (`ApiGamesController`): the state of the game as the authenticated player sees it, or an account that does not play it (a spectator: `viewer_id` null, nothing but what is public, no available action; it watches the game from then on, see "Other services"; a guest or a bot gets a 403), (players with their name and the clan of their stronghold), with a link to the Mercure hub (`Link: <…>; rel="mercure"`, `Mercure\Discovery`), built by `View/GameViewFactory::create(Game, ?Player $viewer)` into the readonly DTOs of `View/Model` (`GameView`, `PlayerView`, `StackView`, `CardView`) and serialized in snake case. A read goes neither through the bus nor through `GameLockMiddleware`. Same errors as the messages API (401, 403, 404). The `ETag` is the version of the game (also `version` in the view): the view only depends on the state and the viewer, so a player sending the ETag they have (`If-None-Match`) gets a 304 until the game changes; the response is `private, no-cache`. The visibility rules only depend on the state, never on the game place, and those of the cards are written once, in `View/Visibility` (shared with the log; a viewer who is not a player, null, sees what every player sees): decks and the opponents' hands are sent as counts (`cards: null`), a face-down card has no `code` (except a province for its owner, and a card set aside for the player of its stack: the player who removed it from the game, the owner of the card it lies under) but its `side` (conflict, dynasty, province…: its back); the secret information of `PlayerState` (`pendingHonorBid`, `strongholdProvinceId`) goes to its owner only (in the factory); everything else is public. A card carries its controller (`controller_id`); a stack of cards under a card, that card (`host_id`). Cards are sent by code: the client reads them from `GET /api/cards`. New secret information must be stored apart from what is public, and masked in the factory. `available_actions` lists the types of the public messages the viewer can send now (`AvailableActionsResolver`, none once the game has ended): an action is listed when its handler's `assertAvailable()` passes, its payload can still be rejected. `special_actions` lists every special message (`{"type", "card_ids"}`, `Service/SpecialActionsResolver`) with the active cards of the viewer whose script needs it (`AbstractCardScript::getSpecialActions()`, see "Card scripts"); none for a spectator.
- `GET /api/cards` and `GET /api/cards/{code}` (`ApiCardsController`): the cards as printed (`LogicalCard`), every card sorted by code or one card, built by `View/LogicalCardViewFactory` into `View/Model/LogicalCardView` (code, printed attributes, `ability_timings`, `ability_granted_to_attached` (read from its script), `image_url`: its image on the CDN of the cards, `<CARD_IMAGES_URL>/cards/<code>.webp`, see "Other services"; not the packs), serialized in snake case. Public (no token) and cacheable, like `GET /api/actions`; 404 `card_not_found` for an unknown code.
- `POST /api/guests` (`ApiGuestsController`): anyone gets a guest account, a human user with the name they chose (`{"name": ...}`, 1 to 64 characters) and no identity, with a session token: 201 `{"user_id", "name", "token"}` (`View/Model/GuestView`), the only time the token is sent. Public.
- `POST /api/accounts` (`ApiAccountsController`): a human creates the account they sign in to, `{"username", "password", "clan"}` (the preferred clan, a Great Clan: the account gets a copy of its starter deck). A guest sends their token and keeps their user and their name (no `name` in the body); anyone else also sends their name at court (`"name"`, 1 to 64 characters) and gets a new user. 201 `{"user_id", "name", "username", "preferred_clan", "settings", "token"}` (`View/Model/AccountView`, also sent by `POST /api/sessions`) with a new session token. Errors: 400 `invalid_payload` (structure: fields missing, not strings or unexpected), 422 `validation_failed` (values, checked by the Validator on `Model/AccountRequest`, and a username taken whatever its case: "This username is taken."), 409 `already_registered` (a token of a user who has an account, or of a bot), 401 an unknown token. Public.
- `POST /api/sessions` and `DELETE /api/sessions/current` (`ApiSessionsController`): signing in, `{"username", "password"}` (the username whatever its case): 201 with a new session token, like an account created; 401 `invalid_credentials`, the same for an unknown username and a wrong password (an unknown username hashes the password too, so that the time does not tell). Each attempt counts against two limits (`config/packages/rate_limiter.yaml`, sliding windows: 5 a minute by username, 20 a minute by IP), a success resets the count of the username: 429 `too_many_attempts` with `Retry-After`. Signing out revokes the session token of the request (204); an API key is not revoked this way (409 `not_a_session_token`). Signing in is public.
- `GET /api/oauth/providers`, `POST /api/oauth/{provider}/authorizations`, `POST /api/oauth/{provider}/sessions` and `GET`, `PUT`, `DELETE /api/self/linked-accounts[/{provider}]` (`ApiOAuthController`): signing in with a provider of identities (OAuth2: authorization code grant with PKCE, the API being the confidential client, `Security/OAuth/OAuthFlow`), once the account is linked to an identity there; accounts are created with a username and a password only. The web client starts a flow (`{"purpose": "sign_in" | "link"}`, with the token of the account to link: 201 `{"authorization_url", "state"}`), sends the human to the provider, which sends them back to the web client (`/oauth/{provider}/callback`, the redirect URI registered at the provider, on the origin of the request); the web client checks the state, then sends `{"code", "state"}` to sign in (201 with a session token, like `POST /api/sessions`; 401 `not_linked`; counted against the limit of its IP) or to link (`PUT /api/self/linked-accounts/{provider}`: 201, 200 when linked already, 409 `provider_already_linked` / `identity_already_linked`). The state (256 bits, used once, 10 minutes in the pool `cache.oauth_state`) keeps the provider, the purpose, the user linking, the redirect URI and the code verifier: 400 `invalid_state` when it does not match. The API exchanges the code (`client_secret`, code verifier) and reads the identifier of the identity; nothing the provider issues reaches the web client. 400 `authorization_failed` when the provider refuses the code, 502 `provider_unavailable`, 403 `account_required` for a guest or a bot, 404 `unknown_provider` (also a provider without credentials). The clients of the providers (`Security/OAuth/OAuthProviderFactory`, league/oauth2-client; `Security/OAuth/Provider`: Google asking `openid` only, Discord `identify`) read their credentials from `OAUTH_<PROVIDER>_CLIENT_ID` and `_CLIENT_SECRET` (empty: disabled) and send their requests through the Guzzle client `app.oauth.http_client`, a `MockHandler` in the tests.
- `POST /api/bot-games` (`ApiBotGamesController`): a game against the house bot, without the queue: the user plays a deck they can use (`{"deck_id": ...}`), the bot another starter deck drawn at random; `Service/GameLauncher/BotGameLauncher` dispatches `CreateGame` then `JoinGame` for the user and the bot. 201 `{"game_id", "player_id", "opponent": {"user_id", "name", "deck_id"}}` (`View/Model/BotGameView`); 422 `deck_not_found`, 503 `bot_unavailable` when the house bot (`HOUSE_BOT_ID`) is not a bot user.
- `GET /api/self` (`ApiSelfController`): the authenticated user, `{"user_id", "name", "username", "preferred_clan", "settings"}` (`View/Model/SelfView`, `username` and `preferred_clan` null for a guest or a bot; `settings`: `{"card_display": "drawn" | "images", "theme": "auto" | "light" | "dark"}`). `PATCH /api/self` `{"name", "preferred_clan", "settings"}` (any of them; a setting left out is kept): changes their name at court (1 to 64 characters), their preferred clan or their settings (400 `invalid_payload`, 422 `validation_failed`), 200 with the user. `DELETE /api/self`: a human deletes their account (204; 403 `account_required` for a guest or a bot), no authentication asked again: `Security/AccountDeleter` takes them and their bots out of the queue, concedes the games they play (`ConcedeGame` through the bus), deletes their invitations, tokens, linked identities and decks (a deck played in a game only loses its name: the player keeps it), and anonymizes the users (`User::anonymize()`: "A former player", no username, password, clan nor settings, the date of the deletion in `deletedAt`), which stay so that the games keep their players. `GET /api/self/subscription`: their subscription to the Mercure hub (`View/Model/SubscriptionView`: the public URL of the hub, their topic and when their subscriber token expires, the token for an hour in the cookie of the hub; `no-store`), see "Other services". `GET /api/self/games`: their games, in progress or ended (not the replays), the last joined first (`View/Model/UserGameView`: id, their `player_id`, `version`, `ended`, `friendly`, the users in player order, the `seats`: each player's user, name, clan of their stronghold and whether a bot plays; once ended, `ended_at`, `winner_id` and `victory_condition`), so that a user matched by the queue finds their game and the history lists their games (`UserGameViewFactory::createAll()`: `GameRepository::findByUser()`, then the clans, two queries).
- `GET /api/decks`, `GET /api/decks/{id}`, `POST /api/decks` and `DELETE /api/decks/{id}` (`ApiDecksController`): the decks the authenticated user can use (their own not deleted and the starter decks; the others are not found, 404 `deck_not_found`), the deletion of one of their own decks (204; 404 for a starter deck, 409 `deck_in_queue` while they wait with it), and the import of a deck: `{"name": ..., "format": "emeralddb", "cards": {"<card id>": <quantity>}}`, 201 with the deck (`View/Model/DeckView`). `Service/Deck/DeckImporter` converts the ids of the format to codes (`Service/Deck/DeckFormatInterface`, one tagged service per format: `codes` for the codes of the engine, `emeralddb` through the external cards), then checks the deckbuilding rules of the Stronghold format (`Service/Deck/DeckConstructionValidator`, not the banned and restricted lists). A deck with the same cards as one of the user's (`contentHash`) is not created: the API answers that deck with a 200 (its name kept), or restores it with a 201 when they had deleted it (with the name of the import); a deck with the cards of a starter deck or of another user is imported as usual (`Model/ImportedDeck`, `Enum/DeckImportOutcome`). Errors: 400 `invalid_payload` (structure, with `violations`), 422 `invalid_deck` (unknown format, card unknown to the format, broken rule; `violations` on `format`, `cards[<id>]` or `cards`). A deck of EmeraldDB is also downloaded from the URL of its page (`Service/Deck/EmeraldDbDeckFetcher`: `/decks/<decklist id>` or `/builder/<deck id>/edit`, read from `/api/decklists/<id>` through the scoped HTTP client `emeralddb.client`, no redirection followed; `InvalidDeckUrlException` for another URL or a deck not shown, `DeckSourceUnavailableException` when EmeraldDB cannot be reached or answers no deck), then imported in the format `emeralddb`: `{"name": ..., "url": ...}` (the name of EmeraldDB unless given; no `format` nor `cards` with a URL), 422 `invalid_deck` with a violation on `url` for a URL naming no deck, 502 `deck_source_unavailable`; also from the console (`app:deck:import <url> --user=<id or username> [--name=]`).
- `GET`, `POST` and `DELETE /api/queue` (`ApiQueueController`): the matchmaking queue. A user joins it with a deck they can use (`{"deck_id": ...}`, 204; 409 `already_queued`, 422 `deck_not_found`) and is matched at once when another candidate waits; `GET` gives the deck they wait with (404 `not_queued` once matched or left). The host of an invitation joins it with its id (`invitation_id`), a friend with its code (`invitation_code`), the bot with the key of the invitation (nothing to add): they are matched together only (422 `invalid_invitation`: unknown, expired, used, not theirs, or its seat taken). The host leaving the queue cancels their invitation.
- `POST /api/invitations`, `GET` and `DELETE /api/self/invitation`, `GET /api/invitations/{code}` (`ApiInvitationsController`, `Service/Invitation/InvitationIssuer`): an account (403 `account_required` for a guest or a bot) invites its bot or a friend to a friendly game (`{"kind": "bot" | "friend"}`, 201 `View/Model/InvitationView`: the code of a friend, or the bot and its key, sent once), which cancels its previous invitation: a host has one waiting at most, read (without the key) or cancelled (404 `invitation_not_found`). The bot is the first bot of the account, else created ("<name>'s bot"). Anyone with the code reads the name of the host and whether it can be used (`pending`, `expired`, `used`; 404 once cancelled): public.
- A replay (its copy) is read by the user who follows it only, as its player: anyone else gets a 404 (`Game::isHiddenFrom()`, the MCP tools too), its view has no available action nor special action, and it has no abandonment (404).
- `GET /api/games/{id}/log?since={version}` (`ApiGamesController`): the log of the game after a version (0 by default) as the authenticated player reads it, or a spectator (only what is public) (`View/GameLogViewFactory`): the messages handled on the game (`version`, `type`, sender `player_id`, never the payload), each with its entries (`template`, `params`) masked for the reader. Same errors and `ETag` as the view, 400 `invalid_since`, 400 `invalid_wait`. It is also a long-poll: with `wait={seconds}` (0 to 30), the response waits until the version is greater than `since` (`Service/GameUpdateWaiter`, polling the version in the database through the Symfony clock), then sends what changed, or the log as is (no message, or a 304) once the time is up; a game that has ended answers at once.
- `GET` and `POST /api/games/{id}/abandonment` (`ApiAbandonmentController`, `Service/Abandonment/AbandonmentClaimer`): whether the authenticated player may end a game their opponent no longer plays (`View/Model/AbandonmentView`: `awaited_player_ids`, `claimable_at`, `claimable`; `no-store`: it depends on the time), then ending it (204 with the `ETag` of the game, which has ended: the player wins), see "Abandoned games". 403 for whoever does not play it, 404 unknown game, 409 `game_not_abandoned` while the opponent may still play (with the time from which they may not) or when the game waits for the player, 412 when the game changes meanwhile.
- `GET /api/games` (`ApiGamesController`): the games in progress (started, not ended), the last started first, for an account to choose one to watch (403 `account_required` for a guest or a bot): `View/GameInProgressViewFactory` into `View/Model/GameInProgressView` (id, `version`, `place`, `friendly`, the players with their name, the clan of their stronghold and whether they are a bot, the number of `spectators`), in three queries whatever their number. `GET /api/games/{id}/spectators`: the accounts watching the game, in their order of arrival (`View/Model/SpectatorView`: `user_id`, `name`), for whoever reads the game (a player or a spectator, who watches it then); `no-store`. `DELETE /api/games/{id}/spectators/self`: the spectator stops watching (204).
- `GET`, `POST /api/games/{id}/replay` and `POST /api/games/{id}/replay/proceed` (`ApiReplayController`): the replay of a game that has ended, for one of its players (see "Replay"). `POST …/replay` starts it again from the beginning (the replay they followed deleted), `POST …/proceed` continues it; both replay up to the next action of the player, which the replay stops before, or up to a version (`{"until_version": n}`, whoever sends the events: going back is starting again up to it). They answer where it stands (`View/Model/ReplayView`: the game, the copy (`replay_game_id`) and the player in it, `version`, `total`, `next`: the next action of the player, `{"version", "type"}`, whose entries the log of the original game tells, and `ended`; `no-store`), as does `GET` (404 `replay_not_found` before it starts); the board is the view and the log of the copy, as its player. 403 for whoever did not play the game, 404 for an unknown game or a replay, 409 `game_not_ended`, 409 `replay_ahead` (proceeding to a version before the replay), 409 `replay_diverged` (an event the engine refuses, with the `version` the copy stands at), 400 `invalid_payload`. `GET /api/games/{id}/replay/log`: the log of the original game as the player reads it (`GameLogViewFactory`), its ids translated into those of the copy, every message of it, those not replayed yet included (`no-store`).
- MCP server (`symfony/mcp-bundle`, `config/packages/mcp.yaml`): `/api/mcp` (HTTP transport), for the programs playing as a bot (`ROLE_BOT`, API key in `Authorization: Bearer`, under the firewall of the API). Its protection against DNS rebinding accepts any host and checks the `Origin`: the host is checked by Symfony for the whole application, against `SYMFONY_TRUSTED_HOSTS` (regular expressions separated by commas, localhost by default; another host gets a 400). Its tools are services of `src/Mcp` with a `#[McpTool]` method: the doc comment of the method and its `@param` describe the tool, the types and `#[Schema]` give the schema of the arguments, which the server checks before the call; a tool returns an array (the structured content) and reports an error with a `ToolCallException`. The user is read through `Security`. The tools give a bot what the HTTP API gives a player, so that an agent needs nothing else: `list_decks`, `join_queue` / `leave_queue` (`Service/MatchMaking/MatchMakingQueue`, shared with `/api/queue`; with the key of an invitation, the bot waits for its host only), `list_my_games` and `wait_for_game` (the long-poll on the games of the bot, until one is in progress: `Service/GameStartWaiter`), `get_game` (the view of `GameViewFactory`), `get_cards` (cards by code, up to 50), `list_glossary_entries` / `get_glossary_entries` (the glossary of the rules entry by entry, by title or term: `Service/Rules/Glossary`), `wait_for_update`, the long-poll on the log (`Service/GameUpdateWaiter`, `GameLogViewFactory`), and `end_abandoned_game` (`AbandonmentClaimer`, the opponent of the bot no longer playing). A list is returned in an object (`{"games": [...]}`), the structured content of a tool being an object. Each public message is also a tool named after its type (`Mcp/MessageToolLoader`, an `mcp.loader` registering a `Mcp/MessageTool` per message): its arguments are the schema of the payload (`MessageSchemaFactory`) with `game_id` and an optional `expected_version`; it returns the new `version`, and a rejected message is a tool error whose text is the problem of the HTTP API. A new public message is a new tool, with nothing to write. The bundle builds PSR-7 messages with `nyholm/psr7`. What a bot is told comes from the server, so that any MCP client plays with a prompt of one line: the `instructions` of the server (how to play: the tools, the loop, the engine as a board, conceding on an error), the rules as resources (`Mcp/RulesResources`: `kyuden://rules/learn_to_play`, `timing_and_gameplay`, `card_clarifications`, read from `doc/`) and the prompt `play` (`Mcp/PlayPrompt`, the line the screen of an invitation shows). `agent/` makes Claude Code play as a bot through this server (`agent/play.sh <API key> [deck]`, with `mcp.json`): it runs in an empty temporary directory, nothing of the repository, with the tools of the server and the reading of its resources only.
- Console commands (`src/Command`) drive the engine; `app:game:log <id> [--as=<user>]` shows the log as a player (or a spectator) reads it.

### Web client (`front/`)

The site of the players, a single-page application (Vue 3, vue-router, Vite, TypeScript) that only talks to the HTTP API, on the same origin. In development, the `node` service runs the Vite server and FrankenPHP (the `symfony` service, `docker/dev/symfony/Caddyfile`) sends it every path but `/api` and `/bundles`, which go to Symfony, and the Mercure hub; in production, `npm run build` gives static files (`front/dist`) for FrankenPHP, every unknown path falling back to `index.html`. Desktop and tablet: designed for 1536px, at least 1133px wide (an iPad mini in landscape: `min-width` of the body); the screens of a game take the visible height (`100dvh`). Not for phones yet. Touch screens get the same screens: what a tooltip tells is also written where a click leads (the effect of a ring in its window, under the ring chosen and under each ring to switch with), a press held half a second on an element with a tooltip shows it above the finger until the next touch, without clicking the element (`lib/tooltip.ts`; no callout nor selection there, `.has-tip`), the hover styles apply only where the device can hover (`@media (hover: hover)`), and the labels of the icons of a card opened are written under them on a touch screen only (`@media (hover: none)`). Installable (a PWA, `vite-plugin-pwa` in `vite.config.ts`, the build only): the manifest (`manifest.webmanifest`, the icons of `public/icons`, from the ensō of the logo) and a service worker (`sw.js`, Workbox) that precaches the shell of the client (`index.html`, the scripts, the styles) and opens the routes of the client from it, never what Symfony and the hub serve (`/api`, `/.well-known`, `/bundles`); a new release replaces it at once and reloads the open pages (`registerType: 'autoUpdate'`), the game being read again from the API.

### Workflows

Six `state_machine` workflows defined in PHP in `config/packages/workflows.php` (Symfony 7.4 array-shape config, `App::config()`; keys are checked by PHPStan against `config/reference.php`): `game` plus one per card type (e.g. dynasty card: `draw_card`, `turn_faceup`, `turn_facedown`, `play`, `discard`). Use the place constants of the card classes and enums in metadata (`StackType::Hand`, `Orientation::FaceUp`), and the helpers of `Workflow/WorkflowConfig` (`transition()`, `cardWorkflow()`, `bowAndReady()`, `triggerAbility()`). Only the `game` places carrying metadata are declared (`places`); the others come from the transitions. Audit trail is on (`workflow` log channel).

**Card place = stack type + orientation.** A card's workflow place is not stored: `PhysicalCard::getCurrentPlace()` computes it with the `getPlace(StackType, Orientation)` mapping of each card class (e.g. a province `UpsideDown` is broken, a dynasty card `FaceUp` in a province is `on_province_faceup`). A place stands for a set of available transitions, so orientations that do not change them share a place: a bowed card (`Sideways`) is still `in_play`, and `bow` / `ready` are transitions from `in_play` to itself. Only what is not a physical position (honor status, fate tokens…) goes in the card `state`. Card workflows use `Workflow/CardMarkingStore`, which reads that computed place and, after a transition, checks that the card really ended up in the target place.

Card transitions declare their effect in metadata, applied by the generic `Workflow/CardTransitionListener`: `stack` (StackType the card moves to), `orientation` (Orientation it takes; required on a move, otherwise the card keeps its orientation) and `position` (`bottom`: at the bottom of the stack, on top otherwise; a card can move within its stack, e.g. to the bottom of its deck). Target stack: a character entering play gets a new stack (`PhysicalCard::entersPlayInNewStack()`); otherwise the context `stack` (e.g. the character or province an attachment goes on, possibly an opponent's), else the player's unique stack. `CardMarkingStore` rejects a target stack the card cannot be in. Write a specific listener only for what metadata cannot express, like `Workflow/LeavePlayListener` (consequences of any transition out of `in_play`: personal honor, tokens, control, attachments, conflict participation), `Workflow/HostLeaveListener` (the cards under a card discarded once it leaves its place) or `Workflow/TakeControlListener` (`take_control`: the controller in the context, the character moved with its attachments to a new stack of its controller). Never move or turn a card outside a transition.

The `game` workflow models the round sequence; a new place exists when the phase **and** the available player actions differ. Place metadata:

- `action_window`: players can trigger action abilities (`TriggerActionAbility`) and play cards (`PlayCharacter`, `PlayAttachment`, `PlayActionEvent`); `play_from_hand: false` forbids characters and attachments (1.4), wherever they are played from. `OpportunityService::assertCanTakeAction()` checks it. The `trigger_ability` transition of a card workflow (from a place to itself) lists where the abilities of a card can be used (`TriggerActionAbility`, `TriggerInterruptAbility`, `TriggerReactionAbility`).
- `opportunities`: players have opportunities to act, in player order or simultaneously, and can pass them (`PassOpportunity`); the step ends once every player has passed (`AllPlayersPassedGuardListener`). Its value is an `Enum/PassingRule`: `Final` (passing forfeits the remaining opportunities of the step) or `Consecutive` (action windows: a player who acts cancels the passes, and the window closes once every player has passed consecutively).

Transition metadata: `auto` and `priority` (see `WorkflowTransitionMiddleware`), and `log`, the template of the entry the transition writes in the log of the game (required on every transition of every workflow, see "Game log"). `end_game` leads from every place of a started game (`WorkflowConfig::placesOf()`) to the final place `game_ended` (`Game::STATE_ENDED`); it is automatic with the highest priority, so the game ends as soon as a player meets a victory condition, before any other automatic transition.

Behaviour lives in listeners under `src/Workflow/<WorkflowName>/`, named after the transition/place and the event type: `...GuardListener` (blocks a transition until conditions are met), `...TransitionListener`, `...EnterListener`.

### Game flow

- **Values from players**: since the engine does not apply card effects, a step whose outcome cards can modify (e.g. the amount of fate collected) is a player action carrying the value; an `auto` transition guarded on every player having acted then moves the game on.
- **Turn records**: what a player did during the round goes in the turn records of `PlayerState`, reset at the end of the round (`fate_phase_ended`).
- **Player order**: stored in `GameState` (`playerIds`, fixed by `start_game` from the order of arrival, `Player::joinRank`; the first player changes, not the order).
- **Opportunities to act**: the players who have the opportunity to act are the active players of `GameState` (`activePlayerIds`); the handler of each action rejects a player who is not active (`NotActivePlayerException`). The enter listener of the step activates them (`FirstPlayerOpportunityEnterListener` and `AllPlayersOpportunityEnterListener` cover the common cases):
  - in steps resolved in player order, only the first player: the handler gives the opportunity to act to the next player (`GameState::getNextPlayerId()` / `getPlayerIdsAfter()`, resolved with `Game::getPlayer()`). An action that requires follow-up actions keeps the opportunity with the player, who ends it with `EndResolution` (see below);
  - in steps where players act simultaneously (e.g. `reveal_honor_dials`, the `react_to_*` reaction windows of a conflict), every player: they keep their opportunity until they pass.

  A player who passes (`PassOpportunity`, in a place marked `opportunities`; `PlayerState::passed`, reset by the enter listener of the step) is no longer active and is skipped by `Service/OpportunityService`. In an action window (`PassingRule::Consecutive`), a player who ends their action (`EndResolution`) resets every pass, so the players who had passed get opportunities to act again.
- **Resolving what a player plays**: an active player who has done nothing passes (`PassOpportunity`); once they act (`PlayActionEvent`, `TriggerActionAbility`, `PlayCharacter`, `PlayAttachment`, `PlayCharacterFromProvince`: `OpportunityService::takeAction()`, `PlayerState::acted`), they apply its effects with other messages, then end it (`EndResolution`), which ends their opportunity: they cannot pass meanwhile (`ResolutionInProgressException`), and `EndResolution` is rejected when there is nothing to end (`NothingToResolveException`). An interrupt or a reaction (`PlayInterruptEvent`, `PlayReactionEvent`, `TriggerInterruptAbility`, `TriggerReactionAbility`) is resolved the same way by any player, without using an opportunity to act, and `EndResolution` ends the last one not ended first, during a duel too; the action itself ends once no duel is being resolved. The events played and the abilities triggered (not the characters and attachments played) are recorded in `PlayerState::resolutions` (`State/Model/Resolution`: the card whose text it is, an attachment for the abilities it grants, and the timing), in the order they were initiated: an interrupt or a reaction leaves it when it ends, the events and abilities of the action with it; the interrupts and reactions not ended yet are counted from it. `available_actions` therefore never lists both `pass_opportunity` and `end_resolution`, and the view of each player shows `acted`, `resolving_interrupts_and_reactions` and `resolutions` (`View/Model/ResolutionView`: the card as the viewer sees it now, by `Visibility`, nothing once it no longer exists, and the timing), so that the players see which effect is being applied. Phase actions that move the game on (declaring a conflict, defenders, a bid…) and `InitiateDuel` (an effect of an ability) are not actions to end.
- **End of the game**: `Service/VictoryService` checks the victory conditions from the state (a player with 25 or more honor wins; a player who has conceded (`ConcedeGame`, `PlayerState::conceded`) or has no honor is eliminated and the last one standing wins; ties go to the first player, then in player order). The guard of `end_game` uses it, and its transition listener records `winnerId` and `victoryCondition` in `GameState`. Honor cannot go below 0 (`PlayerState::setHonor()`).
- **Abandoned games** (`Service/Abandonment`): the player left alone ends the game, which they win (`ClaimAbandonment`, a platform message: the players it waited for are eliminated, `PlayerState::abandoned`, victory condition `abandonment`, `GameAbandonedEvent`). The game waits for the players to whom an action moving it on is available (`AwaitedPlayersResolver`, asking the handlers: passing, ending the resolution, bidding, declaring a conflict, defenders, a total, a dueling statistic, ending a duel…), the defending player while the attacked province is face down, the players with a face-down dynasty card while they are revealed; the effects on the board, available to everybody, move nothing on. A player may end it once it has waited for their opponents only (not for them) for 3 minutes without changing (`AbandonmentClaimer::INACTIVITY`), or for 1 minute once the opponent no longer reads it (`PlayerPresence`: not seen for `ABSENT_AFTER`, 60 seconds; every read of a player through the HTTP API or the MCP tools writes `Player::lastSeenAt`, at most every 10 seconds, in a statement of its own). The time is checked by `AbandonmentClaimer` before sending the message, with the version it checked (`ExpectedVersionStamp`, the entity manager cleared so that the lock reads the game again); the handler only checks the state, so that the events replay. Nothing else ends a game while a player still reads it: the player may wait longer. A game every player has left, unchanged and read by none of them for an hour (`AbandonedGamesEnder::LEFT_AFTER`), is ended by the platform (`EndAbandonedGame`, a platform message: every player eliminated, nobody wins: `winnerId` null, victory condition `abandonment`, `GameEndedWithoutWinnerEvent`), so that both players gone or the human gone in a game of the house bot (which never reads the game nor claims) do not stay in progress: the task `Task/EndAbandonedGames` of the worker, every 5 minutes (`App\Schedule`), finds them in one query (`GameRepository::findLeftSince()`) and sends the message on each with the version it read.
- **Duels**: a duel is not a place of the `game` workflow, since it returns to the action window it was initiated in: it is the `DuelState` of `GameState`, whose steps the messages move on (`InitiateDuel`, `BidHonor`, `DeclareDuelStatistic`, `EndDuel`). While a duel is being resolved, no action window is open and the players cannot pass or end their action (`OpportunityService::assertNoDuel()`); interrupts and reactions can be ended.
- **Interrupts and reactions** are initiated when their triggering condition occurs, not during an opportunity to act: `PlayInterruptEvent`, `PlayReactionEvent`, `TriggerInterruptAbility` and `TriggerReactionAbility` are accepted from any player in any place, during a duel too, and change no opportunity: the player ends them with `EndResolution`. Action events and abilities (`PlayActionEvent`, `TriggerActionAbility`) require the opportunity to act in an action window. An event is played with the message of its timing (`AbilityTiming`), whatever the hand holds (an event may be played from elsewhere, and the decks are secret); the abilities of cards are not checked against their timings, since cards gain and lose abilities.
- **Secret information**: what a player knows and their opponents do not is stored apart from what is public, so that its visibility only depends on the state (e.g. `PlayerState::pendingHonorBid`, the secret bid, and `honorBid`, the revealed one).
- **Mulligan** (glossary, Mulligan; setup 6 and 7): once the provinces are filled (`setup_game`), the game waits in `dynasty_mulligan`, then, once the starting hands are drawn (`dynasty_mulligan_ended`), in `conflict_mulligan`. In each, the players mulligan in player order, from the first player (`MulliganEnterListener`, the handler giving the opportunity to the next player; `MulliganEndedGuardListener` lets the step end once nobody is active): `MulliganDynastyCards` (face-down dynasty cards of their regular provinces) and `MulliganConflictCards` (cards of their hand), with the cards to set aside, none to keep them (`MulliganDeclinedEvent`, "{player} keeps their cards"). As many cards are put into the provinces or drawn from the top of the deck, then the cards chosen are shuffled back into it (`Service/MulliganService`, `CardsMulliganedEvent`). The face-down dynasty cards are hidden from their owner too (the visibility only depends on the state): entering the dynasty mulligan, each player looks at the cards of their provinces (`CardInspector`, in the log for them only), and again once they have mulliganed, so that the client shows them while the step lasts. A game has a mulligan when `CreateGame` says so (`mulligan`, `GameState::mulligan`): the queue and the invitations (`AutomaticGameLauncher`) and `app:game:create`, not the games of the house bot, whose introductory game goes straight to the board, nor the games created before (false by default, so that their events replay the same); without it, both places are passed at once.
- **Refilling the provinces**: once a dynasty card has left a province (played from it, discarded) and no dynasty card remains on it (a holding keeps it from being refilled), the engine refills it, face down, from the dynasty deck of its owner, once the effect is resolved: "after all reaction opportunities to that card leaving the province are passed" (glossary, Refill a Province). The handlers moving dynasty cards out of provinces schedule the province (`Service/ProvinceRefiller::schedule()`, `GameState::provincesToRefill`), and `ProvinceRefillMiddleware` refills the scheduled provinces still empty after each message, once nobody resolves what they have played (an action not ended, an interrupt or a reaction) and no duel is being resolved: a character played from a province is replaced once its player ends the action. The framework steps refill at once (the broken provinces of the fate phase). `FillProvince` remains for setup and the effects that fill a province or add a card to it: the top card of the dynasty deck of its owner onto a regular province, face down or face up (`face_up`: Rally, refilling face up), whatever lies on it already (City of the Rich Frog); a province filled by an effect before the engine refills it is not refilled.
- **Playing from elsewhere than the hand** (Kunshu, Artisan Academy, Prepared Ambush, Gateway to Meido…): `PlayCharacter`, `PlayAttachment` and the events take a card of any player from where a card of its class is played (`Service/PlayService`): a conflict card of a hand, a conflict deck (any card: one looked at before) or a conflict discard pile; a dynasty character face up in a province, of a dynasty deck or a dynasty discard pile; a card set aside (removed from the game, under a card: Stolen Secrets, Back-Alley Hideaway). The effect allowing it is not checked; the opportunity, the action window and the resolution are those of a card in hand. The sender controls what they play (`take_control` once in play when they do not own it: both are logged, the play as `{player} plays {card}…`, the player of the context of the transition), an event goes to the discard pile of its owner (`play_event`), and a province a character leaves is refilled once the action is ended. `PlayCharacterFromProvince` remains the play of the dynasty phase.
- **Costs and effects**: board manipulations (`BowCard`, `LoseHonor`, `GainFate` / `LoseFate`, `DiscardCard`, `HonorCharacter`, `MoveToConflict`…) are accepted in any place, from any player of the game, on any card or player, since the engine does not know which ability is being resolved.
- **Switching the conflict type** (`SwitchConflictType`): an effect accepted in any place during a conflict, from any player; the type toggles.
- **Conflict opportunities by an effect**: `GrantConflictOpportunity` (`target_player_id`, `type`) gives a player an additional conflict of a type this round: one more conflict opportunity (`PlayerState::conflictOpportunities`) and one more conflict of that type allowed (`additionalConflictTypes`, beside `declaredConflictTypes`; `PlayerState::canDeclareConflict()`, and `declarable_conflict_types` in the view of the player), until the end of the round; the conflict phase goes on while a player has an opportunity left. `DeclareNextConflict` (`target_player_id`, a player with an opportunity left) makes the target declare the next conflict out of order, with one of their own opportunities (`GameState::nextConflictPlayerId`, read and cleared by `DeclareConflictEnterListener` before the order, which goes on after them; cleared when the phase begins). Accepted in any place, from any player, for any player; the limits of the cards ("Max 1 per phase") are the players' business.
- **Rings**: the place of a ring is the contested ring, the unclaimed ring pool or the claimed ring pool of a player, where it keeps the type of the conflict it was claimed in (`RingState::claimedConflictType`, which card effects refer to). `SwitchRing` switches the places of two rings, in any place, from any player: a ring going to a claimed ring pool takes the type of the ring it replaces, the conflict keeps its type, and the contested ring is only switched with a ring of the pools of the attacking player, who takes the fate on the new contested ring. `ClaimRing` makes a player claim a ring they have not claimed: nobody's, in the type of the conflict being resolved or the type given (the winner of the conflict does not claim a contested ring claimed this way), or another player's, taken from them in the type it was claimed in unless another is given (`RingTakenEvent`). `ReturnRing` returns a claimed ring to the unclaimed ring pool with its fate (not the contested ring: a conflict always has a ring). `PlaceFateOnRing` and `RemoveFateFromRing` place fate from the general token pool on any ring, or return it there.
- **Looking at cards and revealing them** (`LookAtCards`, `RevealCards`: the top cards of a deck, a hand (or cards of it drawn at random by the generator of the game, `random`: Court of Justice, Kitsuki Chiari) or the dynasty cards in the provinces (`Enum/HiddenPile`, an entry of the log per province), of any player; `LookAtCard`, `RevealCard`: a card): nothing changes in the state; the log gives the cards to the players who learn them (`Service/CardInspector`: the sender and those who already see them for a look, every player for a reveal), the others read how many cards and where. The client of the sender keeps them in sight until the player is done with them.
- **Hands and decks** (`AddCardToHand`: a conflict card of a deck or a conflict discard pile; `PutCardOnDeck`: on top or at the bottom; `ShuffleIntoDeck`; `DiscardCard`, from a deck too): effects accepted in any place, from any player, on any card; a card leaving play or a province follows the same rules as a discard.
- **Putting cards into play** (`PutCharacterIntoPlay`: a character of a hand, face up in a province, of a deck (a card looked at), of a discard pile or set aside, at home or into the conflict on the side of its controller, its owner or the player given (`controller_id`); `PutAttachmentIntoPlay`: an attachment of a hand, a conflict deck, a conflict discard pile or set aside, onto a character in play or a province (`target_card_id`), under the control of its owner or the player given; `PutHoldingIntoProvince`: a holding of the dynasty deck, the dynasty discard pile or set aside into a regular province of its owner): effects accepted in any place, from any player, on any card, without cost nor opportunity to act; a province a character leaves is refilled, a province a holding enters keeps its cards and is no longer refilled while the holding remains (Rebuild: the card shuffled out of the province is not replaced, the holding being there once the effect is resolved).
- **Moving fate** (`MoveFate`): from a holder to another, a fate pool, a character in play or a ring (`Enum/FateHolder`); the fate from or to the general token pool is gained, lost, placed or removed with the other messages (`PlaceFateOnRing` and `RemoveFateFromRing` for a ring).
- **Revealing the attacked province**: once a conflict is declared, the game waits in `reveal_attacked_province` (the defending player active) until the attacked province is faceup, before the reactions to the declaration; a province already faceup passes the step at once. The defending player reveals it with `RevealProvince`, which turns any facedown province face up, of any player (card effects reveal provinces), in any place. `TurnProvinceFacedown` (special) turns an unbroken face-up province face down, with its cards and its tokens, keeping its id (Kitsuki Yaruma, Untamed Steppe…); the Eminent keyword is not checked.
- **Redistributing the cards of the provinces** (`RedistributeProvinceCards`, special: `target_player_id`, `card_ids` and the regular province of each, `province_ids`; Governor's Spy, once `LookAtCards` on the provinces): the face-up cards are turned face down where they are (`turn_facedown`, logged: a holding returns its honor tokens, the cards under it are discarded), then every card is deleted and created again face down in its province, with a new id drawn from the generator of the game (as a shuffle, `StackShuffler`), without a transition, so that the log tells the other players that the provinces were redistributed (`ProvinceCardsRedistributedEvent`), not where each card went; a province left without a dynasty card is refilled once the effect is resolved. The stronghold province takes no part; "each province ends up with at least one card" is not checked.
- **Control** (`TakeControl`, glossary "Control and Ownership"): the controller of a card is its owner unless another player has taken control of it in play (`CardState::controllerId`, read through `Service/ControlService`). The sender takes control of a character or an attachment in play, in any place, of any player (its owner taking it back the same way: the engine does not end effects such as "until the end of the conflict"); the transition `take_control` logs it ("{controller} takes control of {card}"). A character in play is always in a stack of its controller (`Player::getCharactersInPlay()` reads the stacks): it moves there with its attachments, which keep their controller, keeps its state and participates on the side of its new controller. The rules read the controller: participating, defending, being evaded, duels, abilities, moving to the conflict, the honor of a character leaving play. Leaving play ends the control (its `CardState` is reset): the card goes to an out-of-play area of its owner.
- **Other effects on the board** (`MoveAttachment`: an attachment in play to another character in play or a province, keeping its owner; `SwitchProvinceCards`: two dynasty cards of different provinces of the same player, each keeping its orientation; `PutCardIntoProvince`: a dynasty card of a dynasty deck (known through `LookAtCards`), a dynasty discard pile, a province or in play (it leaves play) into another province of its owner, the stronghold province included, face up or face down (`face_up`), beside the cards there, the province it leaves being refilled (transitions `move_to_province_faceup` and `move_to_province_facedown`); `BreakProvince`: a face-up province outside of the resolution of a conflict, a broken stronghold province ending the game; `TakeFirstPlayerToken`: the first player changes, not the player order; `DiscardImperialFavor`: the Imperial Favor returns to its unclaimed state, refused when nobody has it; `TakeImperialFavor`: a player claims it, from its unclaimed state or from a player, on the side given, without moving the game on, unlike `ClaimImperialFavor` after the glory count): accepted in any place, from any player, on any card or player.
- **Setting cards aside** (out of play): `RemoveFromGame` (`face_down`: Stolen Secrets) puts a card into the cards its owner has removed from the game (Shadow Step), or, face down, into those of the sender, who alone knows it then (the card stolen is not shown to its owner); `PlaceCardUnder` (`host_card_id`, `face_down`) puts a card under a card in play (a character, an attachment), a dynasty card face up in a province (Back-Alley Hideaway), a province (Kaiu Shihobu) or a stronghold (Under Siege), the owner of that card knowing it when it is face down (Daidoji Uji). Both take a card of a deck, a hand, a province, play or a discard pile, or a card already set aside (transitions `remove_from_game` and `place_under`, with their `_facedown` variants, `WorkflowConfig::setAside()`); a card leaving play follows the rules of a discard, a province it leaves is refilled. From there, a card is played (`Service/PlayService`), put into play, into a province (`PutCardIntoProvince`, `PutHoldingIntoProvince`), into a hand (`AddCardToHand`), on a deck or into the discard pile. The cards under a card in play or in a province are discarded once it leaves its place (`Workflow/HostLeaveListener`; a bow, a change of control or of province is not leaving it), and their stack removed. Accepted in any place, from any player, on any card.
- **Status tokens** (glossary, "Status Token"): a character in play or a province holds one at most of each kind (`CardState::personalHonor`, read by `ConflictService::assertCanHoldStatusToken()`). `PlaceStatusToken` (`token`: `Enum/StatusToken`, honored or dishonored) places one on a character in play or a province, any kind on either (the engine does not check that only a dishonored token goes on a province); `DiscardStatusToken` discards the token of a character in play or a province; `MoveStatusToken` moves the token of a character to another. A card receiving a token takes its status, or returns to ordinary status when it had the other token, both being discarded; a card cannot receive a second token of a kind. The cards become ordinary or take the status without being honored nor dishonored (`StatusTokenPlacedEvent`, `StatusTokenDiscardedEvent`, `StatusTokenMovedEvent`, not `PersonalHonorChangedEvent`), so that what reacts to honoring or dishonoring is not triggered; accepted in any place, from any player, on any player's cards. Tainted status tokens are not modeled.
- **Honor tokens** (counters, not status tokens: Fortified Assembly, Public Forum, Distinguished Dojo, Endless Archives): `PlaceHonorTokens` and `RemoveHonorTokens` (`card_id`, `amount`) place them from the token pool on a province or a holding face up in a province (`ConflictService::assertCanHoldHonorTokens()`), or return them there; the honor of the players does not change (`CardState::honorTokens`, `HonorTokensPlacedEvent`, `HonorTokensRemovedEvent`). A holding leaving play (leaving its province face up: discarded, sacrificed…) returns its tokens to the pool (`Workflow/DynastyCard/ProvinceFaceupLeaveListener`); switched to another province, it keeps them. Accepted in any place, from any player, on any player's cards.
- **Pointing at a card** (`PointAtCard`): changes nothing but the log ("{player} points at {card} in {stack}"), so that a player shows a card to the opponent; accepted in any place, from any player, on a card of a stack every player sees (not a deck nor a hand), face down included (its code stays masked).
- **Totals from players**: the engine does not compute skills, province strengths or glory, which card effects modify: players declare them (`DeclareConflictSkill`, `DeclareProvinceStrength`, `DeclareGloryCount`) and the engine applies the rules to the declared values (winner, broken provinces, Imperial Favor). The current skill of a character can also be recorded for every player to see (`SetCharacterSkill` / `ResetCharacterSkill`, every modifier applied, cleared when it leaves play); it is not used by the engine.

### Card scripts

What the text of a card means for a game in progress is its script: a subclass of `AbstractCardScript` named after its code (`KakitaKaezin01` for `01-kakita-kaezin`, in `src/CardScript`, which holds `AbstractCardScript` and the scripts only, no pack nor cycle in the namespace), created by `make:app:card-script <code> [--timing=<timing>…] [--granted-to-attached] [--special-action=<type>…]` (`Maker/MakeCardScript`). A card whose text needs nothing has no script. `AbstractCardScript` declares the code (`getCode()`, static) and a method per hook, with a default doing nothing that a card overrides: what is printed on the card, `getAbilityTimings()` (the timings of its triggered abilities, those it grants included: `Enum/AbilityTiming`, action, interrupt, reaction) and `isAbilityGrantedToAttached()` (the attachments whose abilities belong to the card they are attached to, "Attached character gains…"), which `CardScriptRegistry` reads by code for the events played (`PlayService`), the controller of an ability (`AbilityService`) and `GET /api/cards` (none for a card without script); and, given the physical card and the game, `getSpecialActions()`, the special messages its text needs (as classes). The scripts are tagged services found by code (`Service/CardScript/CardScriptRegistry`, a service locator indexed by `getCode()`), stateless and shared by every game: the state stays in the game, so that replaying its events gives the same game, and nothing is registered per game (the house bot plays several games in a request). The services using the scripts are apart, in `Service/CardScript`: `ActiveCardsResolver` gives the active cards of a player, those whose effects they can apply, with their scripts (`Model/ActiveCard`): the cards they control in play and the cards they own out of play, among those whose face they know (`Visibility`: not their decks nor their facedown dynasty cards), so that what the scripts tell them reveals nothing they do not know. A script informs the players (the actions offered…), it never decides: the engine does not enforce the card rules. A test checks that every class of `src/CardScript` is a script named after the code of a card of the fixtures, and only needs special messages.

### Game log

Every change of the state of a game writes an entry in its log (`GameLogEntry`): a template in English whose placeholders (`{player} loses {amount} honor`) are replaced by its params, so that the log can be read as is and translated by the client. The entry belongs to the version of the game the message being handled leads to, automatic transitions included; a message writes any number of entries, ordered by id. The log is written by `GameLog/GameLogger`, from three sources:

- **Card transitions**: `GameLog/CardTransitionLogListener` writes the `log` metadata of the transition, when the card leaves its place (before the consequences of the transition), with the params `card`, `owner`, `from` and `to` (stacks), and `host` (the card it goes under) for an `Underneath` stack.
- **Game transitions**: `GameLog/GameTransitionLogListener` writes the `log` metadata of the transition (no params), before its listeners.
- **Domain events**: a domain event of `src/Event` carrying the `#[GameLog('template')]` attribute (and implementing `Event/GameEventInterface`) writes its entry when it is dispatched, before its other listeners (`GameLog/GameLogEventListener`, registered by `App\Kernel` for every such event); the placeholders name its properties. Every change of the state that is not a transition dispatches one. Bookkeeping that follows from a logged transition is not logged: active players and passes reset when a step begins, turn records, honor dials reset, conflict and duel cleanup.

The log tells *what* changed, not why (the engine does not know the card effects); the client gets the type and the sender of each message beside its entries.

**Visibility of the params** (`GameLog/LogParam`): a param is `player`, `card`, `stack`, `ring`, `value` or `list`. A card or a value may be known to some players only: its visibility is null when public, else the list of the ids of the players who know it (empty: nobody). It is computed when the entry is written, from the state: a card is known to the players who see it before or after the transition (`View/Visibility`: its id when they see its stack, its code when they see its face), a property of an event marked `#[VisibleTo('player')]` only to that player (`#[VisibleTo]`: nobody), a card marked `#[Revealed]` to every player. `View/GameLogViewFactory` masks the log for each reader: a hidden card has no id nor code (no code when only its id is known), a hidden value has `hidden: true`; a reader who is not a player (spectators, to come) only sees what is public.

### Other services

- House bot (`Service/Bot`): the bot of the platform, Kyūden no Karō (user `HOUSE_BOT_ID`, `kyuden-bot` in the fixtures, owned by the user `kyuden`; `app:house-bot:create` creates both when missing, and renames the bot when its name is not `HouseBotCreateCommand::NAME`) plays the games of `POST /api/bot-games`. It plays in the worker: once a message has been handled (after the commit), `HouseBotMiddleware` (first of the bus) wakes it (`HouseBot::wake()`), which sends its turn to the worker (the task `Task/PlayHouseBotTurn`) when it plays the game, which has not ended, every message its own (none skipped as a duplicate: the worker may already have played the turn of the first message of a request), except those the bot sends itself; the worker plays it at once (`LISTEN`/`NOTIFY`), through the bus like any player, until it has nothing to do (at most 100 actions per turn): before each message it clears the entity manager, so that `GameLockMiddleware` loads the game again, and sends the version it decided on (`ExpectedVersionStamp`): a stale version makes it decide again. Its opponent never waits for it in vain: a turn waits in the transport while the worker is stopped, and a worker killed while playing it plays it again; a failure (a bug of the strategy, an action the engine refuses) is logged, then the bot does nothing in the step if it can (pass the opportunity, end the resolution, pass the conflict, declare no defenders), else concedes (`ConcedeGame`, its reason the failure: the players are not told why). The player sees its moves through the notifications of the game. `BotStrategy` chooses the action from the available ones, reading the board through `BoardReader` (the current skills, glory, dueling statistics and province strengths, computed from the cards like the web client prefills them; only what a player sees: a face-down province of the opponent has an assumed strength): it plays the characters of its provinces (the most expensive it can afford, with the fate it will not spend), declares the conflicts it expects to win as if the opponent defended with every ready character (breaking a province first, with the fewest attackers), defends to win or to keep its province, resolves the effect of the ring it wins (`RingEffectChooser`, which reads its own messages since the step began in the events of the game), bids in duels and declares its statistic, and does what the framework steps require (stronghold province, keeping its cards should a game of its own have a mulligan, revealing its facedown dynasty cards and the province it defends, fate of its stronghold, honor bid of 1, the totals, the Imperial Favor on its military side). It plays no conflict card, triggers no ability and ends no duel; it passes every other opportunity. `app:bot:play <game>` makes it play in a game.
- Replay (`Service/Replay/GameReplayer`): a game that has ended is rebuilt from its events for one of its players, on a copy under another id: the events are dispatched again (`EventPlayer`), their payloads translated (`Model/ReplayIdTranslator`: the id of the game becomes that of the copy, every other id has the salt of the original swapped for that of the copy, so that it names what the copy generated from the same seed; the user and the deck of a player joining are kept). Once created, the copy is marked as the replay of the original for the user (`Game::markAsReplay()`, one replay per user and game: starting again deletes the previous one, `GameRepository::delete()`, in SQL), and kept between two steps (`find()`, `getStep()`). `proceed()` replays the next event whoever sends it (the action the replay stopped before), then the events up to the next one the player sent (a public message), excluded, or to the end; or up to a version given (`Model/ReplayStep`: the versions, the next event of the player, whether it has ended). The messages carry a `ReplayStamp` (`Middleware/Stamp`), so that nobody is notified (`GameUpdatedNotificationMiddleware`) and the house bot does not play (`HouseBotMiddleware`); `GameReplayMiddleware` rejects every other message on the copy. The copy records its own events, from which its log is read, and is listed nowhere (the queries of the games in progress, of the games of a user, of the abandoned games skip it). An event the engine refuses stops the replay at its version (`ReplayDivergedException`: an engine or a deck changed since, or a game created before its ids were salted); `findDivergence()` compares the log of the copy with that of the original, version by version (keys sorted: `jsonb` does not keep their order), ids translated. The task `Task/DeleteStaleReplays` of the worker, every 5 minutes (`App\Schedule`), deletes the copies their user has not read for an hour (`StaleReplaysDeleter`, `Player::lastSeenAt` of their player in the copy); deleting an account deletes its replays. `app:game:replay <game> --as=<user> [--step]` replays a game in a transaction rolled back (nothing of the copy stays), showing its log as the player reads it, the next action before each stop (waiting for Enter with `--step`), then whether the copy is identical to the game.
- Images of the cards: a WebP per card, named by its code (`cards/<code>.webp`), in the bucket `kyuden-images` of Cloudflare R2, under a version (`v1/`, so that they are cached for a year, `immutable`: an image changed goes under a new version) and served by Cloudflare on `images.kyuden.app` (the zone `kyuden.app` is at Cloudflare, the site itself not proxied). The API names them (`CARD_IMAGES_URL`, `https://images.kyuden.app/v1` by default, in development and in the tests too); the images of the printings (`Printing::imageUrl`, from the fixtures) are kept as data, not used. Uploaded with rclone, from a directory out of the repository: `rclone copy <dir>/cards r2:kyuden-images/v1/cards --exclude .DS_Store --header-upload "Cache-Control: public, max-age=31536000, immutable"`.
- Card database (`Service/CardDatabase/CardDatabaseImporter`, `app:cards:import`): the cycles, the packs (each naming its cycle, `cycle_id`), the cards as printed, the printings, the external cards and the starter decks, read from the JSON files of `fixtures/`; what exists is updated, what is missing is created, nothing is deleted, so that it runs again on a database in use (each start in production). The fixtures load the cards the same way (`AppFixtures`), then the users of development (`UserFixtures`).
- Matchmaking: `Service/MatchMaking/FifoMatchMakingService` pairs the two candidates of an invitation together only, whoever came first (a friendly game), and the others in their order of arrival, holding the lock of the queue (`CandidateRepository::withQueueLock()`, a PostgreSQL advisory lock); `Service/GameLauncher/AutomaticGameLauncher` creates the game through the bus (`CreateGame`, then `JoinGame` for each candidate: recorded as events, the game starts once both have joined) and removes the candidates. It runs when a user joins the queue (`MatchMakingQueue`, for the HTTP API and the MCP tools), or with `app:matchmaking`.
- Spectators (`Service/Spectating/SpectatorRegistry`): an account reading a game it does not play (its view, its log or its spectators) watches it, until it leaves or has not read it for 45 seconds (`TIMEOUT`: the web client reads a game at least every 15 seconds, the long-poll of the log lasts 30 at most); a game that has ended is not watched. `SpectatorRepository` writes in SQL (an upsert: two reads at once); whoever reads the game removes the spectators who stopped reading, and a spectator reading a game removes those of every game not read for an hour (`PURGE_AFTER`: ended, abandoned). Each arrival and departure is announced to the players and the spectators (`SpectatorsUpdatedNotification`, `spectators_updated` on `/games/{id}`, with the id of the game only), who read the spectators again; `GameUpdatedNotification` also goes to the spectators. A deleted account no longer watches anything.
- Worker: the tasks done out of the requests are messages of `src/Task` (`Task/TaskInterface`, each with its handler beside it, registered on `task.bus` only: `#[AsMessageHandler(bus: 'task.bus')]`), dispatched on `task.bus` (no middleware of the actions but `doctrine_ping_connection`: a task dispatches the actions it needs on `default.bus`, each in its own transaction) and routed to the transport `async` (Doctrine, the table `messenger_messages`, the worker woken at once by `LISTEN`/`NOTIFY`), which the worker consumes (the service `worker` in development and in production, from the image of the application). The recurring tasks are on the schedule of the application (`App\Schedule`, Symfony Scheduler, stateful in `cache.app`: ending the abandoned games, deleting the replays nobody reads), whose transport `scheduler_default` the same worker consumes: `messenger:consume async scheduler_default --bus=task.bus` (a message of the schedule carries no bus: every message received goes to `task.bus`). A task holds ids and reads the state again, and may be handled twice (a worker killed while handling it gets it again after 5 minutes, `redeliver_timeout`; a failure is retried 3 times, then kept in the transport `failed`): its handler does nothing when there is nothing left to do. The worker stops after an hour (and after 256 MB in production) and is started again by Docker; it keeps the code it loaded (`make worker-restart` in development). In the tests, `async` is in memory: a test reads the tasks sent from the transport and invokes their handler.
- Notifications: `NotificationInterface` objects sent through `NotifierInterface`; `MercureNotifier` publishes them as private updates of the hub, `LoggerNotifier` logs them.
- Security: stateless access-token authentication: `Security/AccessTokenHandler` finds the `AccessToken` by the hash of the token, with its `User` (a single query; an unknown token gets a 401, the key of an invitation no longer valid too), and keeps it for the request (`Security/CurrentAccessToken`). A user is matched to the player of a game through `Player::user`. `Security/AccessTokenIssuer` issues the tokens (random, prefixed `l5r_`, returned once). The password of a human only gets a session token (`POST /api/sessions`); the API also issues one to a guest (`POST /api/guests`) and to an account created (`POST /api/accounts`). The bot of an account and the key of an invitation come with the invitation of the bot; other bots and their API keys are created by console commands (`app:user:create`, with `--username` for a human who signs in: the password is asked; `app:token:create`, `app:token:revoke`), and the fixtures hold users with known tokens and passwords (`DataFixtures/UserFixtures`, in clear, development and tests only: john and jane have an account, with a preferred clan and their copy of its starter deck, harry and sally are guests).
- Mercure: every topic is private (`Notification/Topics`): `/games/{id}` (`game_updated`: its id and version, no data of the game; `spectators_updated`: its id) and `/users/{id}` (`game_started`). A subscriber sends a token (`Notifier/SubscriptionFactory`, `GET /api/self/subscription`) whose `subscribe` grant is the topic of the user (`exact`) and a URL pattern of the topics of their games (`urlpattern`, `/users/{id}/games/:gameId`); an update of a game also carries that topic for each of its players and spectators (`Topics::ofGame()`), so that the token of a user reads every game they play or watch, joined before or after it was issued, and no other. The hub speaks the protocol 1.0 (no compatibility mode), and so does Symfony (`config/packages/mercure.yaml`): the tokens are RFC 9068 access tokens (`at+jwt`, `authorization_details`), signed with `MERCURE_JWT_SECRET`, from the issuer `https://kyuden.app` that the hub trusts (its `issuer` block) for the resource identifier the hub is given (`resource_identifier`, also the base of the relative topics and patterns), the same wherever it is reached; the subject of a subscriber token is its user. The protocol accepts no token in the URL, and browsers cannot set headers on an `EventSource`: `GET /api/self/subscription` sets the token in a cookie (`mercure_access_token`, the `cookie_name` of the hub and of the bundle: not prefixed with `__Secure-`, so that plain HTTP keeps it, secure over HTTPS), HTTP only, `SameSite=Strict`, on the path of the hub, for an hour; the browser sends it to the hub with the subscription (`match` for each topic, `last_event_id` to resume). The hub is the one FrankenPHP embeds, on the origin of the site: the server publishes to it inside its container (`MERCURE_URL`), the browsers subscribe to `MERCURE_PUBLIC_URL`, a relative URL (no anonymous subscriber, no CORS).
- Exceptions: `Exception/Data` (missing/mismatched data) vs `Exception/Rules` (game-rule violations).
